# پیشرفت پایلوت معماری فن‌آسا

تاریخ: ۱۰ اکتبر ۲۰۲۶. مالک هماهنگی: «Fanasa Platform Control Center» — `01a1220e-88e3-73e2-abc0-02b5deef731c`.

اولویت تازهٔ مستقیم کاربر در چت «Neo»، تمرکز همهٔ چت‌ها بر UI/UX تا اطلاع ثانوی است. ادامهٔ اتصال مشترک Lua/PCC/Usage پیش از generation، build و اجرای آزمون نگه داشته شد؛ [فایل‌های مستقل آن](pilot/tests/Fanasa.GatewayUsage.Pilot.Tests/DRAFT-STATUS.md) پیش‌نویس‌اند و هیچ نتیجهٔ موفق جدیدی ندارند. ابزار موقت Lua با کنترل مسیر حذف شد: ۱۵ فایل و ۵٬۳۷۵٬۴۰۶ بایت؛ کد و قفل نسخه حفظ شدند. ادامهٔ این چت، پیش‌نمایش تعاملی مرکز راهبری داخل همان برنامه است، با دادهٔ نمایشی برای رفتارهای فاقد بک‌اند. شاهدهای runtime پایین همچنان مستقل و معتبر در دامنهٔ ثبت‌شدهٔ خود باقی‌اند.

پایلوت تجاری هنوز پذیرفته نشده است. هماهنگ‌کننده به VPS وصل شد، سه image رسمی با هویت ثابت را از مسیر انتقال خصوصی وارد Docker موجود کرد و آزمون محدود یک Gateway را با **۱۲ بررسی موفق** اجرا کرد؛ پروژهٔ آزمایشی سپس با موفقیت متوقف شد. [شاهد native](pilot/native-smoke-orchestration-3.json) و [سلامت پس از اجرا](pilot/vps-postflight-3.json) ثبت‌اند. پذیرش یک مسیر Managed موجود، با owner و consumer متفاوت، به سه گیت زیر نیاز دارد. [معماری](ARCHITECTURE.md)، [برنامهٔ رشد](GROWTH-AND-DEVELOPMENT-PLAN.md) و [هماهنگی اجرا](EXECUTION-COORDINATION.md) حدود و مالکیت را تعیین می‌کنند.

این سند وضعیت جاری را جایگزین ادعای تاریخی «چت‌ها ادامهٔ اجرایی ندارند» می‌کند. سابقهٔ ارسال، تعارض active writer و اصلاح compatibility در سند هماهنگی و [گزارش اتصال محلی](INTEGRATION-REPORT.md) حفظ است. شمار و hashهای گزارش اتصال شاهد ثابت همان تحویل‌اند و به نتیجهٔ runtime جدید تبدیل نشده‌اند.

## شواهد ثابت compatibility

گزارش اتصال محلی، ۱۷۱ بررسی سیاست، ۶۵ آزمون Gateway با ۱۴ حالت مشترک، ۵۳ بررسی اتصال Accounting، ۶۲ بررسی regression و ۲۶ بررسی ساختاری را ثبت کرده است. این مجموعه‌ها بعضاً تو‌در‌تو هستند و مجموع مستقل ندارند. همان Decision تولیدشده و witness قطعی محلی، برای یک commit مصنوعی فقط یک debit ساختند؛ duplicate/replay debit دوم نساخت. binding، هویت، قیمت و backend آن مرحله مصنوعی‌اند.

hashها و نسخه‌های [گزارش اتصال](INTEGRATION-REPORT.md) مبنای تاریخی همان خروجی‌اند. ۸۷ آزمون harness، ۲۴۱ بررسی C# و ۲۴۸ بررسی محصول، تحویل‌های بعدی با دامنه‌های متفاوت‌اند؛ جای hashها و پذیرش پیشین را نمی‌گیرند. این سند suiteها را دوباره اجرا نکرده است و نتیجه را از شواهد تحویل محلی و ادامهٔ چت‌های بررسی‌شده نقل می‌کند.

## گیت ۱: native، ظرفیت و بازیابی

بستهٔ Gateway و [runbook native](../../../NeoCluster/fanasa-platform-workstreams/api-gateway/native/README.md) آماده‌اند؛ [بازبینی مرزها](../../../NeoCluster/fanasa-platform-workstreams/api-gateway/native/BOUNDARY-REVIEW.md) محدودیت witness و provisioning را روشن می‌کند. گیت با ثبت نسخه و digest واقعی imageها، بارگذاری همان plugin/module/script، پذیرش schema و startup، ترافیک واقعی OIDC/PDP/Redis/backend TLS و نتیجهٔ runner پذیرفته می‌شود. ورود مجاز، Deny، token/tenant نادرست، missing PEP، گواهی نامعتبر، timeout/تصمیم منقضی و Redis unavailable باید نتیجهٔ مثبت/منفی و شمار invocation backend داشته باشند.

دو route و چند replica باید از allocation مشترک مصرف کنند؛ amendment و suspend/revoke سهمیه را reset نکنند. Redis restart/restore، no-eviction، AOF/backup، ACL و رفتار unknown outcome باید شاهد مستقل داشته باشند. ظرفیت با CPU/RAM، latency/error، TPS/burst/quota و backlog همین slice اندازه‌گیری می‌شود؛ بودجهٔ پیشنهادی resource، وعدهٔ ظرفیت نیست. اجرای harness سه replica، دستور استقرار سه Gateway روی VPS نیست.

در میزبان Windows، Docker/Podman یا WSL قابل اجرا گزارش نشده است. [inventory زندهٔ VPS](pilot/vps-native-inventory.json) چهار CPU، حدود ۷۹۴۱ MiB RAM کل، ۱۶۸۶ تا ۱۷۵۴ MiB RAM در دسترس، حدود ۱۰۶٫۸۶ GiB دیسک آزاد، Docker 29.6.1، Compose 5.3.1 و K3s v1.33.13+k3s2 را ثبت کرد. آزمون فقط‌خواندنی Compose، امکانات config/resource caps/internal network/build reset را تأیید کرد؛ نسخهٔ major ۵ به دلیل نام نسخه رد نمی‌شود.

آزمون کامل چهار container APISIX، با سقف مجموع ۱۴۰۸ MiB، حداقل ۲ GiB RAM در دسترس می‌خواهد و اکنون از این گیت عبور نمی‌کند. [محدودیت منابع](pilot/compose.resources.yaml)، [overlay آزمون یک Gateway](pilot/compose.smoke.yaml) و [راهنمای اجرای محدود](pilot/NATIVE-RUN.md) آماده‌اند. اجرای محدود یک Gateway، با سقف ۶۴۰ MiB و ۰٫۵۵ CPU، شاهد مستقل smoke است و پذیرش سه replica محسوب نمی‌شود. نسخهٔ پایهٔ Python فقط پس از probe داشتن Python/OpenSSL استفاده می‌شود و build نامحدود روی VPS اجرا نمی‌شود.

تلاش واقعی اجرای smoke روی VPS در [گزارش orchestration](pilot/native-smoke-orchestration-2.json) ثبت شد. hash بسته و ۲۴ فایل و model واقعی Compose با capهای دقیق، شبکهٔ internal و صفر پورت عمومی پذیرفته شدند. دریافت image پایهٔ Python با exit ۱ شکست خورد؛ مرحلهٔ cert و startup هیچ Gateway اجرا نشد و هیچ case ترافیک native پذیرفته نشده است. cleanup پروژهٔ اختصاصی موفق بود. تلاش قبلی فقط به اعتبارسنجی نحوهٔ نمایش عدد در JSON Compose برخورد کرد؛ اعداد integer و رشتهٔ canonical با همان مقدار دقیق پذیرفته شدند، بدون کاهش cap.

[تشخیص فقط‌خواندنی رجیستری](pilot/registry-preflight.json) نشان داد Docker Hub و سرویس auth از VPS timeout دارند، mirror پیکربندی‌شده وجود ندارد و سه image نسخه‌دار لازم در cache Docker نیستند. Redisهای موجود در K3s به نسخه‌های دیگری تعلق دارند و جایگزین نشده‌اند. مأموریت تحویل آفلاین به «از گیت تا دپلوی» ارسال شد، اما نوبت تازهٔ آن شاهد اجرای artifact نداشت؛ تیم داخلی هماهنگ‌کننده دریافت و تحویل را واقعاً انجام داد.

سه image دقیق `python:3.12.10-slim-bookworm`، `redis:7.4.6-bookworm` و `apache/apisix:3.14.1-debian` از registry رسمی روی Windows دریافت شدند. [lock](pilot/official-images-linux-amd64.lock.json)، [گزارش export](pilot/official-images-export.json) و [بازبینی منبع](pilot/official-images-source-audit.json) اصل manifest/config، ۲۱ لایهٔ مشترک و DiffIDهای بازشده را تأیید می‌کنند. archive به اندازهٔ ۲۰۹٬۳۷۷٬۲۸۰ بایت، با SHA-256 `ca1bc7fc668c5a9157bc991801e5bc30b4c7908df2d861a43a4bb9e3ecdbecc0`، پس از بررسی مستقل محدودهٔ دقیق سه image با SFTP منتقل و یک بار در Docker موجود load شد. [شاهد انتقال و import](pilot/image-delivery.json) هویت واقعی Linux/amd64 و ترتیب لایه‌ها را تأیید می‌کند؛ Docker 29 اینجا image ID را digest همان selected manifest گزارش کرد.

[تلاش سوم](pilot/native-smoke-orchestration-3.json) بدون pull/build و با pin به image IDهای تأییدشده موفق شد: capability probe، cert initialization، startup و ۱۲ case native اجرا شدند. درخواست مجاز status ۲۰۰، یک admission مصرف‌شده و یک forwarding به backend داشت. identity غیرفعال ۴۰۱، PDP Deny برابر ۴۰۳ و دسترسی مستقیم بدون گواهی مشتری رد شدند؛ Denyها forwarding نساختند. source بسته ثابت ماند، OOM رخ نداد و cleanup فقط همان پروژه موفق بود. [اختلاف currentness](pilot/package-currentness.json) در snapshot همان smoke فقط دو README جدیدتر داشت؛ کد اجرایی در آن زمان با بستهٔ ثابت ۲۴فایلی یکسان بود. توسعهٔ بعدی Gateway/receiver در این اجرای قدیمی حضور نداشت.

Gateway در snapshot پس از runner حدود ۳۹٫۸۶ MiB و Redis حدود ۱۰٫۹۳ MiB مصرف داشتند؛ این اعداد peak یا وعدهٔ TPS/ظرفیت تولید نیستند. cap مجموع ۶۴۰ MiB/۰٫۵۵ CPU و صفر پورت عمومی حفظ شد. [postflight](pilot/vps-postflight-3.json) RAM آزاد ۲٬۰۳۱٬۴۶۸٬۵۴۴ بایت، K3s فعال، node ready و Portal انتخاب‌شده ready را ثبت کرد؛ گیت ۲ GiB full acceptance همچنان رد است. daemon، firewall، mirror، اعتماد TLS و quota تغییر نکردند.

quota توسعه نیز ۱۲ PVC از ۱۲ و ۱۲ GiB storage از ۱۲ را مصرف کرده است؛ پایلوت مجوز تغییر سهمیه یا ایجاد PVC تازه از این snapshot نمی‌گیرد. node و deployment انتخاب‌شدهٔ Portal ready بودند؛ این inventory، بررسی سلامت تمام محصولات یا provenance ثبت محصول سازمان نیست.

## گیت ۲: احراز رمزنگاری و tenant در backend

۷۷ بررسی Bearer و ۱۱۴ بررسی PCC، baselineهای مرحلهٔ قبلی‌اند. اجرای جدید [PCC و publication](pilot/central-gateway-verification.json) **۱۳۴ موفق، صفر خطا و exit صفر** داشت و ۱۶ hash منبع ثابت ماندند. ۲۰ case جدید رسید observed، HTTP 202 پیش از مشاهده، تطبیق hash اصلی NeoContract، mismatch زمان/نسخه، rollback مجوز، replay و reopen را آزمودند. کنترل مجموعهٔ دقیق completion، تصمیم تازه و deadline اصلی حفظ شد. داده و امضاهای این suite مصنوعی‌اند و receiver واقعی Gateway را به‌تنهایی تأیید نمی‌کنند.

backend باید Bearer اصلی را با مرجع اعتماد پیکربندی‌شده و امضای رمزنگاری معتبر بررسی کند و issuer، audience/client، زمان و scope لازم را enforce کند. tenant از هویت معتبر و رکورد داده کنترل می‌شود؛ header یا body مشتری، role، Decision ID و admission ID به‌خودی‌خود اختیار نمی‌دهند. registry مرکزی durable، tenant و عضویت فعال و grant صریح پایدار شرط‌اند. مسیر مستقیم و caller فاقد مجوز باید پیش از mutation و charge رد شوند.

پذیرش به آزمون مثبت consumer مجاز و آزمون‌های منفی امضای خراب، issuer/audience اشتباه، انقضا، هویت/tenant خارجی، grant لغوشده، جعل header/context و bypass مستقیم نیاز دارد. شاهد هر رد باید ثابت کند business/history/receipt/usage/ledger تغییر نکرده‌اند. ادغام فقط در میزبان و storeهای موجود انجام می‌شود؛ فایل‌های جدید امنیت به‌تنهایی فعال‌سازی route یا اعتماد admission را اثبات نمی‌کنند.

metering و trust واقعی opt-in و پیش‌فرض بسته‌اند. receiver موجود، mTLS واقعی و HMAC روی method/path/Bearer/body/idempotency را می‌سنجد؛ nonce backend پایدار است و guard داخل تراکنش، اختیار و deadline را پیش از commit تازه می‌کند. نبود تنظیمات یا شاهد معتبر اجازهٔ اجرا/debit نمی‌دهد. dedup عملیات/payload در admission Redis و مشاهدهٔ authenticated rollout هنوز تحویل نشده‌اند؛ مصرف nonce به‌تنهایی این دو را ثابت نمی‌کند.

## گیت ۳: یک محصول با منشأ معتبر و admission مورد اعتماد

برای یک محصول Managed موجود، مرجع مرکزی باید product/client/audience/URL و مالک فعال durable، consumer متفاوت، عضویت/grant صریح، قرارداد و amendment امضاشده، نرخ مصوب با snapshot/version و یک allocation پایدار با limits/scope/revision معتبر را ارائه کند. هنوز هیچ‌یک از این ترکیب واقعی برای محصول سازمان در این snapshot اثبات نشده است. fixture `organization-fabric`، client فرضی، قرارداد نمونه یا قیمت تاریخی مصنوعی، provisioning واقعی نیست.

projection و PIP از منابع authoritative و producer احراز‌شده می‌آیند؛ PDP pure می‌ماند. counter provisioning فقط از control plane مجاز و قابل audit انجام می‌شود و درخواست داده allocation/دورهٔ جدید provision نمی‌کند. داشتن credential جدا یا Redis ACL به‌تنهایی ثابت نمی‌کند caller اسکریپت، action `provision` را نمی‌تواند اجرا کند؛ مرز trusted control/admission باید آزموده شود.

کد میزبان ingress producer، projection/PIP/role/policy و receiver امضاشدهٔ Gateway را دارد. publication تغییرناپذیر در همان تراکنش ثبت می‌شود؛ پاسخ HTTP 202 تا مشاهدهٔ معتبر pending/superseded است و HTTP 200 acknowledged فقط برای receipt دقیق، durable و هنوز جاری صادر می‌شود. observer پیش‌فرض unavailable است و endpoint مشاهدهٔ native هنوز لازم است. [ورودی‌های پذیرش محصول واقعی](pilot/REAL-PILOT-READINESS.md) tuple تجاری را مشخص می‌کند؛ قرارداد/نرخ/client/grant واقعی از این تحویل محلی نتیجه نمی‌شوند.

مسیر پذیرفته‌شده یک زنجیرهٔ قابل ردیابی دارد: قرارداد/نرخ/عضویت/grant معتبر → Decision و obligations → admission قطعی مورد اعتماد → کنترل tenant backend و commit → event/snapshot/ledger/outbox موجود. بازخوانی همان operation نباید backend یا debit را تکرار یا قیمت را عوض کند. suspend/revoke، انقضا، کمبود سهمیه و نبود provenance باید رد شوند. witnessهای محلی `organization-permission/v1` و `ledger-credit:` در [راهنمای مصرف](../../products/Fanasa.AccessManagement/docs/USAGE-ACCOUNTING.md) از Decision/admission زنده جدا هستند.

## چارت سازمانی و اتصال HR — ۱۳ اکتبر ۲۰۲۶

[مدل نهایی چارت، هویت و دسترسی](ORGANIZATION-IDENTITY-ACCESS.md) و مراحل رشد ثبت‌اند: OrgRole، سمت و انتصاب از AccessRole و grant جدا هستند؛ ارث‌بری چارت مجوز ضمنی نمی‌دهد. binding دامنه‌دار و provenance/reconciliation انتقال، مرحله بعدی پیاده‌سازی‌اند. HR API محدود روی OrganizationStore/Fabric موجود، هر هفت عملیات مجاز، سه مسیر عمومی و احراز سرویس مستقل دارد.

[پذیرش محلی HR](pilot/hr-api-verification.json) **۱۷۱ بررسی موفق، صفر خطا، exit صفر** و build بدون warning/error دارد. انقضای واقعی token و grant در پردازش Store باعث rollback چارت/history/receipt/outbox شد؛ همان request پس از بازیابی فقط یک‌بار commit شد. گواهی واقعی، جعل header، Cookie، tenant، replay/conflict، history و حفظ listener انسانی آزموده شدند. YAML و JSON منتشرشده، schemaها و routeها نیز ماشین‌خوان تطبیق شدند. این نتیجه جای پذیرش artifact مستقر یا native APISIX را نمی‌گیرد.

[بررسی فقط‌خواندنی توسعه](pilot/hr-api-runtime-readonly.json) روی VPS، **Nginx موجود → HTTPS/mTLS → HR API** را با GET مجاز `200` و اتصال مستقیم بدون گواهی `403` تأیید کرد. نشانی بیرونی `/development/organization-hr/v1` صریحاً به مسیر داخلی `/api/organization-hr/v1` بازنویسی می‌شود؛ `/api/...` روی host عمومی توسعه `404` گرفت. CA/hostname/SNI بررسی شدند؛ اتصال فیزیکی loopback بود چون DNS محلی نام API خطا داشت، پس دسترسی از رایانه مصرف‌کننده هنوز پذیرفته نشده است.

client واقعی `fanasa-organization-hr-development` از قبل برای tenant `hr-development` وجود داشت؛ grants آن در زمان بررسی تا ۱۹ اکتبر معتبر بودند. حساب انسانی بررسی‌شده در `fanasa-internal` عضو است و همان service برای آن tenant مجوز ندارد. هیچ حساب، client، عضویت یا grant جدید در این بررسی ساخته نشد. [راهنمای اتصال و OpenAPI](pilot/HR-API-INTEGRATION.md) محدوده عملیاتی و ورودی‌های اتصال سازمان دیگر را روشن می‌کند. پروفایل APISIX در مالکیت چت Gateway مستقل و خاموش است؛ [شاهد مالک](/E:/SJVS/Projects/NeoCluster/fanasa-platform-workstreams/api-gateway/hr-integration/verification.json) ۳۶ آزمون موفق، ۲ skip روی Windows و exit صفر ثبت می‌کند. native HR و binding عملیاتی بازند؛ شاهد Nginx به APISIX نسبت داده نمی‌شود و ۱۹۳ آزمون عمومی Gateway به شمار HR افزوده نمی‌شود.

## بودجه و مالکیت ادامه

پاک‌سازی این ادامه با مجوز صریح حذف اصل ضبط‌ها کامل شد: **۸۲۵ فایل محلی / ۲٬۳۷۲٬۴۸۸٬۸۱۱ بایت** و **۵۴ فایل VPS / ۲٬۲۶۲٬۷۸۲٬۴۴۳ بایت**. اعداد، مجموع طول فایل‌ها روی هر ماشین‌اند. هر شش اصل ضبط، قطعه‌های موقت، مدل‌های مختص رونویسی، blobهای تکراری و خروجی‌های قابل بازسازی آزمون هماهنگ‌کننده حذف شدند. متن‌ها، گزارش‌ها، metadata، لاگ/JSON آزمون و archive لازم imageهای رسمی حفظ شدند؛ نبود متن خام اصلی ۱ و ۲ پیش از حذف و متن جایگزین ۲ صریحاً ثبت‌اند. [شاهد محلی](pilot/storage-cleanup.json) و [شاهد VPS](pilot/vps-audio-cleanup.json) hashها و محدوده را ثبت می‌کنند؛ worker متوقف نشد و cleanup پس‌زمینه باقی نیست.

اجرای نهایی PCC پس از اصلاح replay، ۱۳۴ موفق/صفر خطا داشت؛ [شاهد اتصال](pilot/central-gateway-verification.json) ۱۶ منبع ثابت و hash DLLهای پیش از پاک‌سازی را نگه می‌دارد. بازبینی مستقل منبع، کنترل receipt تاریخی و flag تغییرناپذیر قبل از mutation را تأیید کرد. suite مستقل HTTPS receiver پس از اصلاح fixture کلید و جداسازی policy بازنشسته **۷۸ موفق/صفر خطا با exit صفر** داشت؛ موفقیت از لاگ واقعی آن ثبت شد. [شاهد مالک ۰٫۴](workstreams/contract-policy/implementation/EVIDENCE.v0.4.0.md) پنج suite با ۹۸۹ check موفق را گزارش می‌کند؛ این شمار، سناریوهای تولیدی متمایز نیست و ۱۳۴ PCC دوباره به آن اضافه نمی‌شود. Lua/APISIX/Redis این اتصال در suite C# اجرا نشده‌اند.

پایلوت با یک PCC موجود، یک Gateway و Redis اختصاصی limiter پیش می‌رود؛ SQLite تک‌میزبان، Keycloak، registry مرکزی، Portal، محصول، Accounting و outbox موجود حفظ می‌شوند. resourceهای Gateway/Redis ابتدا برآوردند و پس از گیت ظرفیت تثبیت می‌شوند. PAP/PIP/PDP و مصرف مرز ماژول دارند؛ registry، broker، workflow engine، DB یا runtime مالی تازه ایجاد نمی‌شود. بازار/تسویه مالک، چند provider و تعمیم External/AI بعد از پذیرش همین slice بررسی می‌شوند.

Gateway مالک native/limiter است؛ سیاست مالک projection/Decision، مصرف مالک event/snapshot/ledger، مدیریت قراردادها مالک business provenance و تیم امنیت مالک فایل‌های جدید backend است. هماهنگ‌کننده ادغام Program/registry/persistence و پذیرش نهایی را انجام می‌دهد. هر ادغام به مسیر فایل، نسخه/hash، نتیجهٔ مثبت/منفی و محدودیت باقی‌مانده نیاز دارد. داده یا مجوز ساختگی برای عبور از گیت‌ها ساخته نمی‌شود؛ پایان این پایلوت نیز تکمیل کل برنامهٔ ۳۸ آیتمی نیست.
