# هماهنگی اجرای معماری فن‌آسا
تاریخ: ۱۰ اکتبر ۲۰۲۶

مرجع هماهنگی: «Fanasa Platform Control Center» — 01a1220e-88e3-73e2-abc0-02b5deef731c.

درخواست کاربر، ادامهٔ چت‌های موجود و توسعهٔ موازی معماری با کنترل پیچیدگی و نگهداری است. چت‌های معماری مورد درخواست ایجاد شده‌اند؛ ادامهٔ فعلی در همان چت‌ها و مسیرهای محصول انجام می‌شود. [معماری](ARCHITECTURE.md) و [پلن توسعه](GROWTH-AND-DEVELOPMENT-PLAN.md) مقصد را تعریف می‌کنند؛ این سند ترتیب و مالکیت کار و [پیشرفت پایلوت](PILOT-PROGRESS.md) شواهد جاری و سه گیت پذیرش بعدی را ثبت می‌کنند.

## وضعیت فعلی تحویل

در ۱۳ اکتبر، فایل‌های مستقل `OrganizationHrApi/Security/Hosting` و آزمون‌ها ذخیره و build شدند؛ ۱۷۱ check محلی موفق با شواهد مستقل ثبت شد. هماهنگ‌کننده قرارداد YAML و JSON منتشرشده را تطبیق داد. مسیر توسعه Nginx موجود به‌صورت فقط‌خواندنی با GET200 و direct403 بررسی شد؛ prefix بیرونی development و prefix داخلی api با rewrite صریح همسو هستند. HR service موجود فقط tenant توسعه را پوشش می‌دهد و ایمیل حساب انسانی grant سرویس ایجاد نکرد. مالک Gateway پروفایل APISIX را در `hr-integration/` با آزمون و وضعیت خاموش مستقل تحویل می‌دهد؛ پذیرش Nginx به APISIX نسبت داده نمی‌شود. گزارش currentness و محدوده آزمون در [راهنمای HR](pilot/HR-API-INTEGRATION.md) است.

درخواست مستقیم بعدی کاربر، تکمیل مدل چارت/هویت/دسترسی و ارائه API منابع انسانی پشت Gateway است. این دامنه در کنار اولویت UI ادامه دارد: هماهنگ‌کننده مالک wiring میزبانی و اسناد، عامل API مالک فایل‌های مستقل HR و آزمون‌ها، و چت «Fanasa API Gateway» مالک route و تنظیمات NeoCluster است. اتصال بر OrganizationStore/Fabric موجود تکیه می‌کند؛ ایجاد مدل شخص/رجیستری/موتور سیاست دوم جزو این کار نیست. وضعیت آزمون و اتصال عملیاتی HR جدا از baselineهای پیشین ثبت می‌شود.

اولویت جاری، طبق پیام مستقیم کاربر در چت «Neo»، UI و UX است؛ استفاده از دادهٔ نمایشی در صفحهٔ فاقد بک‌اند مجاز است. هماهنگ‌کننده فقط `wwwroot/previews/control-center.html` و CSS/JS اختصاصی آن را برای پیش‌نمایش مرکز راهبری ویرایش می‌کند. Layout، Index، Architecture و Platform دارای مالک/تغییرات هم‌زمان‌اند و وارد این ویرایش نمی‌شوند. آزمون مشترک Lua/PCC/Usage پیش از build/run به‌صورت پیش‌نویس حفظ شده؛ توقف این مرحله، نتیجهٔ آزمون یا پذیرش تازه تولید نمی‌کند. دادهٔ نمایشی هیچ قرارداد، grant، نرخ مصوب یا استقرار واقعی نمی‌سازد.

تحویل تاریخی تطبیق محلی سیاست، Gateway و Accounting تکمیل شد: ۱۷۱ بررسی سیاست، ۶۵ آزمون Gateway شامل ۱۴ حالت مشترک، و ۵۳ بررسی اتصال حسابداری، همراه با ۶۲ بررسی regression و ۲۶ بررسی ساختاری، موفق‌اند. این گروه‌ها مستقل و قابل جمع‌زدن نیستند. همان Decision تولیدشده و شاهد admission قطعی استفاده شدند؛ یک commit مصنوعی با duplicate/replay فقط یک debit ساخت. [گزارش اتصال محلی](INTEGRATION-REPORT.md) و hashهای آن، شاهد ثابت همان تحویل‌اند؛ ادامهٔ توسعه وضعیت و شمار آزمون‌های آن مرحله را بازنویسی نمی‌کند.

**وضعیت جاری جایگزین ادعاهای قبلی دربارهٔ نبود ادامهٔ چت‌هاست.** ادامهٔ واقعی Gateway، Contract & XACML، Usage & Accounting و Architecture Integration تأیید شده است. بستهٔ Gateway، ۸۷ آزمون محلی مالک و ۱۲ بررسی محدود native هماهنگ‌کننده روی VPS دارد؛ full acceptance باز است. تحویل سیاست ۳۴۴ بررسی C# را گزارش کرده و اجرای تازهٔ PCC/publication با ۱۳۴ موفق، صفر خطا و منبع ثابت ثبت شده است؛ ۲۴۱ C# و ۱۱۴ PCC شاهدهای پیشین‌اند. مصرف اتصال opt-in به محصول موجود و ۲۴۸ بررسی محصول را گزارش کرده است. جزئیات و مرز پوشش در [پیشرفت پایلوت](PILOT-PROGRESS.md) و [شاهد اتصال مرکزی](pilot/central-gateway-verification.json) آمده‌اند.

هماهنگ‌کننده با SSH و strict host verification به VPS متصل شد و single-Gateway APISIX/Redis/TLS را با ۱۲ بررسی موفق، source ثابت و cleanup همان پروژه اجرا کرد. پذیرش چند replica، ظرفیت/بازیابی و محصول/client، قرارداد امضاشده، نرخ مصوب، grant و provisioning واقعی این پایلوت هنوز باز است. بخش سابقهٔ پایین snapshotهای قدیمی را حفظ می‌کند؛ مرجع وضعیت جاری، این بخش و سند پیشرفت پایلوت است.

## بودجهٔ پیچیدگی

- ابتدا یک محصول Managed موجود، یک API/عملیات، یک allocation و یک consumer متفاوت از owner پذیرفته شود.
- Keycloak، PCC، Portal، محصول و Accounting موجود حفظ شوند. PAP/PIP/PDP و مصرف ابتدا مرز ماژول در PCC موجود دارند؛ interface مستقل به معنای process مستقل نیست.
- APISIX و شمارنده Redis اجزای تازهٔ هدف پایلوت‌اند؛ چت Gateway باید حالت استقرار و وابستگی پیکربندی واقعی APISIX را روشن کند. هیچ نسخه یا حالت نصب در این سند فعال فرض نمی‌شود.
- اجرای پایلوت یک نمونه PCC و Gateway دارد. آزمون چند replica و دو route از allocation مشترک برای اثبات عدم تکثیر سهمیه لازم است؛ این معیار دستور نصب سه replica روی VPS نیست.
- SQLite موجود در پایلوت تک‌میزبان حفظ می‌شود. SQL Server فقط پیش از چندمیزبان‌شدن PCC، با migration/restore پذیرفته‌شده لازم است.
- کنترل tenant، قرارداد، نقش، زمان، تصمیم، obligations و حدود واقعی سهمیه از slice حذف نمی‌شود. پارامتر الزامی پشتیبانی‌نشده مانع عرضه است؛ بی‌اثر یا نامحدود تفسیر نمی‌شود.
- Temporal/BPMS، broker یا mesh تازه، PDP/Accounting مستقل، marketplace/payout، چند provider، GPU scheduler و چارچوب Generalist شرط اولین مسیر API نیستند.
- concurrency و رزرو مالی/چندبعدی فقط اگر محصول و مدل پرداخت همین پایلوت نیاز دارند وارد شوند. برای API کوتاه با نرخ مشخص، ابتدا TPS/burst/quota و مصرف idempotent کافی است.
- هر جزء runtime یا store اضافه باید نیاز فعلی، مالک عملیات، مصرف منابع، روش backup و مسیر حذف/جایگزینی مشخص داشته باشد.

پایلوت محدود، کل برنامه ۳۸ آیتمی را کامل اعلام نمی‌کند. تعمیم External/webhook، فرایند، AI و چندمیزبان پس از پذیرش همین مسیر توسعه می‌یابد.

## جلوگیری از تداخل و قرارداد اتصال

سه قرارداد اتصال اولیه کافی‌اند: ContractAccessProjection/limits، Decision/obligations و UsageEvent. allocationId در همهٔ آن‌ها پایدار و scope از مرجع قرارداد گرفته می‌شود.

چت سیاست مالک schema projection/decision است؛ چت مصرف مالک schema usage است. چت Gateway و محصول با fixture نسخه‌دار مستقل پیش می‌روند. business contract نزد مدیریت قرارداد باقی می‌ماند.

هماهنگ‌کننده، مالک ادغام فایل‌های مشترک Program.cs، registry، persistence، migrations و دو سند مرجع است. چت‌های جدید ابتدا فایل و نمونه مستقل در directory اختصاصی می‌سازند؛ تغییر مشترک را به‌صورت پیشنهاد قابل بررسی تحویل می‌دهند. فایل‌های LSP متعلق به چت LSP، runner/model integration متعلق به پنل کار، صفحه Architecture متعلق به چت نمایش معماری، Portal متعلق به چت پنجره واحد و pipeline متعلق به چت دپلوی است.

## سابقهٔ ارسال و بازیابی آغاز

تمام وضعیت‌ها و شمارهای این بخش، سابقهٔ snapshotهای پیش از به‌روزرسانی جاری‌اند. عبارات «شروع تأیید نشده»، «نوبت اجرایی تازه ایجاد نکرد» و «محدودیت آغاز حل‌شده اعلام نمی‌شود» در ادامهٔ این سابقه، وضعیت فعلی چت‌های دارای شاهد ادامه نیستند و با بخش وضعیت جاری و [پیشرفت پایلوت](PILOT-PROGRESS.md) صریحاً جایگزین شده‌اند. سابقه برای حفظ مسیر بازیابی و مرز شواهد حذف نشده است.

ایجاد هر سه چت و ارسال دستور به هفت چت موجود با پاسخ موفق ابزار ثبت شد. بررسی read_thread/wait_threads نشان داد این ارسال‌ها تا زمان ثبت این سند اقدام تازه یا ابزار اجرایی ایجاد نکرده‌اند؛ بعضی پاسخ‌ها خالی یا «آماده‌ام» بوده‌اند. سه چت تازه در نوبت اولیه و یک پیگیری صریح نیز متن مأموریت قابل مشاهده در تاریخچه نداشتند و پیشرفت نشان ندادند. علت داخلی این رفتار اثبات نشده است؛ موفقیت ارسال با موفقیت آغاز کار یکی نیست.

وضعیت اولیه چت‌ها «مأموریت آماده و پیام ارسال‌شده؛ شروع اجرا تأیید نشده» بود. این مانع هماهنگی را نباید به اتمام کار، نبود مجوز کاربر یا مسدودبودن همهٔ کارهای مستقل تعبیر کرد. شرح مأموریت‌ها در فایل‌های بالا و [دستورهای ادامهٔ چت‌های موجود](/E:/SJVS/Projects/Neo/docs/fanasa-platform-control-center/EXISTING-CHAT-TASKS.md) نگهداری می‌شود. ادامهٔ خودکار فقط پس از شاهد اقدام واقعی تأیید شود؛ برای توقف بی‌تغییر پیام‌های کلی تکرار نشوند.

پیشرفت واقعی باید خواندن منبع مرتبط، خروجی جدید، تغییر/آزمون مرتبط یا مانع دقیق باشد. برای هر ادغام: مسیر فایل، نسخه قرارداد/schema، نتیجه مثبت/منفی و محدودیت باقی‌مانده لازم است. کارها با داده/مجوز ساختگی یا اعلام موفقیت از صرف وجود UI پذیرفته نمی‌شوند.

### به‌روزرسانی با شاهد اقدام واقعی

ارسال پیام بسیار کوتاه برای خواندن و اجرای فایل مأموریت، در چت‌های تازه آغاز واقعی ایجاد کرد. علت ناکامی برخی ارسال‌های قبلی مشخص نشده و حد طول خاصی برای ابزار ادعا نمی‌شود. این روش یک راه بازیابی آزموده‌شده در همین نشست است.

| چت | آخرین شاهد تأییدشده |
| --- | --- |
| Fanasa API Gateway | فعال؛ ۱۱ رخداد ابزار در نوبت بررسی‌شده، مرور منبع و شروع بسته PEP/shared limiter در محدوده اختصاصی |
| Fanasa Contract & XACML | فعال؛ ۱۷ رخداد ابزار، مرور entitlement و آغاز schema/evaluator محدود و pure |
| Fanasa Usage & Accounting | فعال؛ ۱۲ رخداد ابزار، تطبیق دو مسیر usage و Accounting و آغاز fixture تراکنش receipt/ledger/outbox |
| از گیت تا دپلوی | فعال؛ ۱۸ رخداد ابزار، ادامه محلی قراردادهای CI و کنترل انتشار بدون تغییر VPS |
| پنجره واحد | نوبت تازه آغاز شده و خواندن مأموریت در commentary ثبت شده؛ در همان snapshot هنوز رخداد ابزار نداشت، بنابراین اصلاح یا پذیرش اعلام نمی‌شود |

به پنل مدیریت کار و LSP، پیام کوتاه ادامهٔ بخش اختصاصی با پاسخ موفق ارسال شد؛ آغاز عملی آن‌ها در snapshot بالا هنوز تأیید نشده بود. ارسال کوتاه به قرارداد/SSO/نمایش معماری نیز آغاز شد، اما پاسخ بعضی فراخوانی‌های قدیمی با تأخیر برگشت؛ وضعیت نتیجهٔ این ارسال‌ها تا رسیدن شاهد مستقل باز است. پایان انتظار ابزار در چت هماهنگ‌کننده، به معنای توقف یا تکمیل چت مقصد نیست. هیچ چت مقصدی توسط هماهنگ‌کننده متوقف یا آرشیو نشده است.

### کنترل نهایی اسناد

بازبینی فقط‌خواندنی هشت سند هماهنگی، معماری، برنامه و مأموریت‌ها، ۴۱ پیوند محلی را بررسی کرد؛ فایل مقصد مفقودی باقی نماند. دو ارجاع سورس تاریخی `8f13` به مسیر متنی و شاهد snapshot تبدیل شدند و وجود فعلی آن‌ها ادعا نمی‌شود. مرز مالکیت فایل‌ها و بودجه پیچیدگی سازگار بود. معیار Managed در بخش ۱۴ معماری، «پذیرش اولین مسیر پایلوت» است؛ تکمیل آن به معنای تکمیل کل MVP شامل External نیست.

بازخوانی تازهٔ نوبت‌ها در ۱۰ اکتبر، تحویل محلی را تأیید کرد؛ شمار آزمون‌های زیر از گزارش همان چت‌هاست و آزمون اتصال مشترک یا تولید محسوب نمی‌شود.

چت تازهٔ Fanasa Architecture Integration هم در ایجاد و پیگیری کوتاه، فقط پاسخ عمومی داد و ابزار اجرا نکرد. چت بیشتری ایجاد و پیام کلی تکرار نمی‌شود. سه زیرعامل داخلی همین هماهنگ‌کننده، policy_compat، gateway_compat و usage_compat، اجرای واقعی محلی در همان سه directory را آغاز کرده‌اند. مأموریت این تیم فقط اصلاح compatibility است؛ پنج چت قدیمیِ بدون اجرای تازه، ادامه‌داده‌شده یا تمام‌شده اعلام نمی‌شوند. اتوماسیون‌های موجود تغییر نکرده‌اند.

### پایان اصلاح compatibility

تیم داخلی هر سه بسته را تکمیل و source/fixtureهای نهایی را ثابت کرد. Gateway نسخهٔ DTO داخلی سیاست را مصرف می‌کند و هر دو obligation را اعمال/حفظ می‌کند؛ فرمت provisional قبلی شاهد interoperability محسوب نمی‌شود. revision تخصیص مستقل است و مصرف سهمیه با تغییر policy/contract reset نمی‌شود. witness فقط پس از admission قطعی صادر می‌شود و Accounting مصرف همان witness و commit مصنوعی را لازم دارد. دریافت مجدد برای همان business operation debit دوم نساخت. چهار ایراد مرزی بازبینی مستقل اصلاح شدند؛ [گزارش نهایی](INTEGRATION-REPORT.md) و شواهد هر مالک، شمار و دامنهٔ آزمون‌ها را از سابقهٔ مستقل جدا می‌کنند.

کار باقی‌مانده، اتصال و پذیرش محیط واقعی همین پایلوت محدود است: inventory/source/artifact، native Gateway/Redis/TLS، auth transport، provisioning، backend PEP، provenance نرخ/قرارداد و wiring Accounting/outbox. این گام، مجوز ساخت workflow engine، registry یا runtime مالی تازه ایجاد نمی‌کند. محدودیت آغاز پنج چت قدیمی حل‌شده اعلام نمی‌شود؛ هیچ قفل نشست یا کنترل دسترسی دور زده نشد.

کنترل مستقل نهایی هماهنگ‌کننده، اثر انگشت هر سه manifest و خروجی مشترک را بدون mismatch تأیید کرد. پنج کپی حسابداری دقیقاً با خروجی اصلی برابر بودند. ۲۹ سند، ۲۱۶ پیوند محلی و parse شدن ۳۵ JSON بررسی شدند؛ مقصد مفقودی وجود نداشت. نتیجه و مرز این بررسی‌ها در گزارش نهایی ثبت است.

## ادامهٔ فعلی و سه گیت پذیرش

اتصال مرکزی جدید در [گزارش Gateway/PCC](pilot/CENTRAL-GATEWAY-CONNECTION.md) و [شاهد منبع و اجرا](pilot/central-gateway-verification.json) ثبت شده است. هماهنگ‌کننده مالک publication/observed receipt و آزمون ۲۰ case جدید است؛ مالک سیاست receiver/commit guard را تحویل داد و suite مستقل HTTPS با ۷۸ موفق/صفر خطا و exit صفر تمام شد. [شاهد مالک](workstreams/contract-policy/implementation/EVIDENCE.v0.4.0.md) و ۶۰ input/hook manifest، همراه لاگ و DLLها، مستقل تأیید شدند. PCC نهایی روی ۱۶ منبع ثابت ۱۳۴/۰ داشت. observer واقعی native و dedup سهمیه هنوز تحویل نشده‌اند و commercial gate باز نمی‌شود.

پاک‌سازی مجاز اصل شش ضبط و داده‌های تولیدی کامل شد: محلی ۸۲۵ فایل / ۲٬۳۷۲٬۴۸۸٬۸۱۱ بایت، VPS ۵۴ فایل / ۲٬۲۶۲٬۷۸۲٬۴۴۳ بایت. متن‌های موجود، گزارش‌ها و شواهد حفظ شدند؛ نبود raw-primary ۱ و ۲ پیش از حذف ثبت است. نتیجه در [شاهد محلی](pilot/storage-cleanup.json) و [شاهد VPS](pilot/vps-audio-cleanup.json) آمده؛ build مالک چت دست‌نخورده و همهٔ processهای پاک‌سازی هماهنگ‌کننده تمام شده‌اند.

جزئیات شاهد هر چت، تحویل‌های محلی جدید و محدودیت‌های runtime در [پیشرفت پایلوت](PILOT-PROGRESS.md) ثبت است. تیم امنیت backend فقط `OrganizationBearerSecurity.cs` و `OrganizationOperationApi.cs` و آزمون‌های جداگانه را توسعه می‌دهد؛ اتصال فایل‌های مشترک و فعال‌سازی به مالک ادغام تعلق دارد. احراز رمزنگاری Bearer، کنترل tenant داده، عضویت/grant پایدار و admission معتبر باید مستقل پذیرفته شوند. metering پیش‌فرض خاموش و admission مورد اعتماد پیش‌فرض رد است؛ نبود شاهد به اجازه تبدیل نمی‌شود.

ترتیب کار بعدی محدود به سه گیت است: (۱) شاهد native و ظرفیت/بازیابی اندازه‌گیری‌شده، (۲) پذیرش رمزنگاری و tenant در backend، (۳) یک محصول با allocation و منشأ قرارداد/نرخ امضاشده و trusted admission واقعی. همهٔ گیت‌ها برای قبول اولین مسیر لازم‌اند. شمار آزمون‌های محلی یا پایان یک نوبت چت، هیچ‌کدام پذیرش این مسیر یا تکمیل کل برنامه نیستند.

بودجهٔ runtime همان یک PCC، یک Gateway و Redis اختصاصی limiter در پایلوت است؛ سه replica در harness فقط ابزار اثبات quota مشترک‌اند. هیچ registry، broker، workflow engine یا runtime مالی تازه لازم نشده است. چت یا اتوماسیون تازه و بازپردازش صوت در این ادامه ایجاد نمی‌شود؛ provisioning ساختگی برای پرکردن گیت‌ها مجاز نیست.

### پذیرش backend و اتصال واقعی VPS

هماهنگ‌کننده مسیر Bearer مستقل `unit.save` را با یک فراخوانی در Program موجود ثبت کرد؛ پس از اصلاح انقضای JWT هنگام انتظار برای admission، نسخهٔ نهایی ۷۷ بررسی HTTP را با exit صفر گذراند. مجوز، عضویت، client و tenant از رکورد durable کنترل می‌شوند و توکن/هدر جعلی و replay متناقض mutation یا debit ایجاد نمی‌کنند. ثبت این extension فعال‌سازی تجاری نیست: تنظیمات پیش‌فرض خاموش و validator تولیدی admission پیش‌فرض رد است.

ورود SSH با اطلاعات قبلی و strict host verification موفق شد. inventory زنده، Docker/Compose/K3s موجود و ظرفیت را ثبت کرد؛ RAM در دسترس حدود ۱٫۷ GiB، کمتر از گیت ۲ GiB آزمون کامل بود. بستهٔ ۲۴ فایل و hash روی VPS تأیید شد و model smoke محدود ۶۴۰ MiB/۰٫۵۵ CPU بدون پورت عمومی پذیرفته شد؛ دریافت image پایه از Docker Hub شکست خورد. startup و آزمون native اجرا نشدند. cleanup همان پروژهٔ اختصاصی موفق بود و سرویس‌های موجود تغییر نکردند. شواهد و حدود این نتایج در [پیشرفت پایلوت](PILOT-PROGRESS.md) است.

مأموریت عملی تحویل آفلاین imageهای نسخه‌دار، با منبع رسمی و digest/blob hash، به «از گیت تا دپلوی» ارسال شد. مالک این چت، آماده‌سازی artifact است؛ هماهنگ‌کننده مالک انتقال و اجرای محدود VPS می‌ماند. تغییر mirror/firewall/daemon/TLS trust یا تعویض نسخه برای عبور از آزمون مجاز تلقی نشده است. گیت‌های منشأ واقعی قرارداد/نرخ، client/grant و trusted admission همچنان بازند.

### نتیجهٔ اجرای native و ورودی‌های اتصال بعدی

نوبت تازهٔ «از گیت تا دپلوی» اجرای artifact را اثبات نکرد. تیم داخلی همین هماهنگ‌کننده، سه image رسمی دقیق را دریافت و manifest/config/blob/DiffIDها را بررسی کرد؛ هماهنگ‌کننده archive حدود ۲۰۰ MiB را با SSH/SFTP خصوصی منتقل و یک بار در Docker موجود وارد کرد. [شاهد انتقال](pilot/image-delivery.json) و [lock تصاویر](pilot/official-images-linux-amd64.lock.json) ثبت‌اند. تنظیم daemon/firewall/mirror/TLS trust تغییر نکرد.

اجرای واقعی [single-Gateway native](pilot/native-smoke-orchestration-3.json) **۱۲ بررسی موفق**، یک forwarding و یک admission برای درخواست مجاز، ردهای OIDC/PDP/direct-backend، source ثابت، نبود OOM و cleanup موفق همان پروژه را ثبت کرد. این نتیجه، پذیرش چند replica، بازیابی Redis، ظرفیت یا محصول تجاری نیست. [postflight تازه](pilot/vps-postflight-3.json) node/Portal انتخاب‌شده و K3s را سالم ثبت کرد؛ RAM آزاد ۱٫۸۹ GiB همچنان کمتر از گیت ۲ GiB full acceptance است.

کد PCC projection store، ingress producer، PIP/PDP و receiver امضاشدهٔ سازمان را میزبانی می‌کند. انتشار limits و رسید durable به همان Fabric متصل‌اند: پیش از مشاهدهٔ معتبر، HTTP 202 pending/superseded صادر می‌شود؛ ACK دقیق HTTP 200 کنترل مجدد اختیار و نسل را لازم دارد. observer پیش‌فرض unavailable است. [ورودی‌ها و ترتیب محدود اتصال](pilot/REAL-PILOT-READINESS.md) نیاز به endpoint مشاهدهٔ authenticated native، dedup سهمیه و tuple واقعی قرارداد/نرخ/client/grant/allocation را حفظ می‌کند.

suite baseline میزبان PCC، پیش از اتصال Gateway پس از اصلاح fixture CSRF/clock و خطای پذیرش completion ناشناخته، **۱۱۴ موفق/صفر خطا با exit صفر** شد. fixture داده و امضاهای مصنوعی دارد. wrapper completion را snapshot می‌کند و مجموعهٔ دقیق شناسه‌های صادرشده را می‌خواهد؛ case unknown-superset حذف یا به unknown-only تقلیل داده نشده است. هشت hash منبع در اجرای نهایی ثابت بودند. [شاهد پذیرش محلی میزبان](pilot/pcc-host-verification.json) شاهد تاریخی همان مرحله است؛ این نتیجه جای executor Gateway یا tuple تجاری واقعی را نمی‌گیرد.

تلاش اولیهٔ ارسال پیام مشخص هماهنگی به «Fanasa Contract & XACML» با ابزار `send_message_to_thread` از سوی بازبینی خودکار رد شد: مجوز صریح کاربر برای پیام‌دادن به همان چت تشخیص داده نشد. سپس کاربر همین ارسال را صریحاً تأیید کرد و پیام نتیجه و هماهنگی با موفقیت ارسال شد. پیام، پایان اصلاح و نتیجهٔ ۱۱۴/۰ میزبان و ۱۲/۱۲ native، حفظ guard و regressionها و ورودی‌های باقی‌ماندهٔ اتصال واقعی را اعلام می‌کند؛ در آن پیام اولیه، توقف writer درخواست نشد، چون اصلاح baseline تمام شده بود. در ادامه، مالکیت publication نزد هماهنگ‌کننده و receiver/commit guard نزد چت سیاست تعیین شد و هماهنگی جلوگیری از تغییر هم‌زمان فایل‌ها ارسال شد. ارسال موفق پیام، شاهد اجرای نوبت بعدی آن چت نیست. مجوز اتصال VPS موضوع رد اولیه نبود.
