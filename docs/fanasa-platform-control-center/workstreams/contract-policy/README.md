# ContractAccessProjection / Decision — compatibility 2.0.0, native integration 0.4.0

Current source delivery `0.4.0` retains native library build version `0.2.0` and adds an authenticated Gateway Decision endpoint, an opt-in direct mTLS/HMAC request receiver, durable replay protection and transaction commit guards to the [base PCC integration](implementation/PCC-INTEGRATION.md). See [Gateway integration](implementation/PCC-GATEWAY.md) and [verification](implementation/EVIDENCE.v0.4.0.md). The default executor remains unavailable. The following compatibility/reference documentation and historical audit describe earlier independent slices and do not supersede the current integration guides. No live registrations, signed commercial contracts or deployed end-to-end acceptance are asserted.

The local compatibility continuation is authorized by [INTEGRATION-ALIGNMENT.md](../../INTEGRATION-ALIGNMENT.md). It adds one synthetic `organization-fabric / organization.unit.save` profile to the same bounded evaluator. The common binding is [fixture-binding.v1.json](../../integration/fixture-binding.v1.json). No product, grant, contract or allocation is registered or provisioned by these fixtures.

The reusable output is [fixtures/integration-decision.v2.json](fixtures/integration-decision.v2.json), **generated by `evaluate()` through the normalized projector**, with `schemaVersion: 2.0.0` and `profileId: fanasa.contract-policy/2`. Its source projection/context/event are the adjacent `integration-*.v2.json` files. [manifest.v2.json](manifest.v2.json) contains the current source/fixture fingerprints and [INTEGRATION-EVIDENCE.md](INTEGRATION-EVIDENCE.md) records the commands and results. The original v1 schemas, fixtures, tests, manifest and [EVIDENCE.md](EVIDENCE.md) are preserved as historical regression evidence; the historical v1 manifest is not the fingerprint of the updated evaluator.

From this package directory, with Node.js and no package installation:

```powershell
node --test --experimental-test-isolation=none --test-reporter=tap tests/contract-policy.test.cjs tests/integration-policy.test.cjs
node sample/generate-integration-fixture.cjs --check
```

`node sample/generate-integration-fixture.cjs` emits the four-fixture JSON bundle using the actual evaluator. The continuation persisted these exact outputs through the workspace file tool; `--check` verifies every persisted byte against regeneration. This script performs no live provisioning or accounting.

Version 2 has separate identity and key rules. Tenant/principal identity fields accept UUID strings directly, as well as the prior bounded lowercase synthetic slugs. UUID spelling is preserved and equality is exact. Product keys, action keys and the request nonce keep their lowercase leading-letter syntax. The common request reference is `g-aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`, a fixed synthetic stand-in for the Gateway's cryptographic nonce, and is distinct from a business operation UUID. The fixture audience `fanasa-organization-fabric-api` and template `organization-unit-save/1` bind only the organization fixture; they do not establish a live registry binding. The historical Club v1 profile still binds only its Club product/action/audience.

`limits.configRevision` is required in v2, is an independent positive safe integer, and is supplied directly by authoritative allocation configuration. It is never inferred from `contractVersion` or `policyVersion`. The pure projector rejects a lower allocation revision and conflicts on equal revision with different limits. It retains the original allocation identity, scope and counter-key rules; contract/policy/price amendments, suspension, resume and retries do not reset counters. These projector checks cover this one aggregate; Control Plane and the Gateway must validate the authoritative shared allocation when multiple contracts use it. A v1 projection cannot silently migrate into v2 state; explicit migration/provisioning remains an integration requirement.

The two existing obligation IDs and parameter shapes are retained, with `configRevision` added to the admission parameters. `allocationReference` still contains the exact allocation id and canonical scope; it is not narrowed to a route or product. The quota algorithm/period is `fixed-calendar-utc` / `month`, so at the fixture instant the applicable period is `2026-10`, `[2026-10-01T00:00:00Z, 2026-11-01T00:00:00Z)`. A new period must be provisioned by Control Plane; the PDP creates no counters or periods. Zero quota remains zero and requires the admission boundary to deny every request.

Permit requires both obligations. Gateway must bind the resource obligation to trusted consumer/product/environment/action and preserve it for backend data-tenant authorization. Version 2 emits one policy reference; Usage maps it to `fixture-organization-unit-save@3`, maps the Decision reference from `requestId`, and maps the contract reference from `projectionReference` with explicit signed 32-bit contract-version range validation. Gateway returns `admission:` + `requestId` only after confirmed admission; a reference string alone is not authenticated evidence. Re-evaluation/retry must not replace evidence behind an existing Decision reference. This package neither fabricates an absent `decisionId` nor produces a successful admission witness.

Version 2 Permit validity is bounded by contract, membership, grant and trusted PIP evidence and at most 30 seconds after evaluation. Gateway additionally bounds this by token expiry, parses instants without rounding a deadline up, and rechecks immediately before forwarding. The sample PEP helper uses a synthetic fulfilled-ID list solely for local tests; it does not prove an actual counter or backend enforcement result. `api.request.admitted` counts admission attempts; `organization.change` remains a separate committed-business billing meter. Permit and admission do not create a charge.

This continuation adds no general policy engine, identity alias registry, persistence, server, counter, ledger or runtime wiring. Native APISIX/Redis/TLS, trusted producer/PIP transport, backend tenant enforcement, live rates and real product/contract acceptance remain subsequent integration gates. The DTO is custom Fanasa JSON, with no claim of full OASIS XACML conformance.

## محصول نمونه و نگاشت پارامترها

`club / report.read` یک انتخاب **مصنوعی آفلاین** برای شکل یک محصول Managed است. این profile فقط زوج `club` و audience `fanasa-club-api` را می‌پذیرد؛ محصول دیگر نیازمند profile جدید با binding محصول/audience معتبر registry است. ثبت Managed واقعی، API `report.read`، audience، tenantها، grant و قرارداد مستقر اثبات نشده‌اند. شناسه `club` پیش از اتصال باید در profile بررسی‌شده جدید به کلید واقعی registry نگاشت شود. owner برابر `tenant-a` و consumer برابر `tenant-b` است؛ تفاوت آن‌ها مانع مجوز SaaS نیست.

| پارامتر | type / unit / scope / range | required / default / mergeRule | اثر و محل اعمال |
| --- | --- | --- | --- |
| Rule / feature | action ID؛ فقط `report.read` در template `report-read/1` | required؛ بدون default؛ intersection حقوق شناخته‌شده | target محصول و action؛ همه شروط لازم AND؛ explicit Deny مقدم |
| Role | array؛ فقط `ApiInvoker`؛ consumer/product/action | required؛ array خالی یعنی بدون eligibility؛ intersection | eligibility برای binding صریح؛ خرید هیچ role یا grant و `platform.admin` نمی‌سازد |
| Seat | integer 0..1,000,000؛ active-membership؛ consumer/product/subscription | required؛ بدون default؛ min سقف هم‌واحد/هم‌scope | پذیرش اتمیک عضویت/assignment در Tenancy؛ PDP هیچ seat نمی‌گیرد؛ offboarding همیشه مسیر مستقل دارد |
| TPS | number >0 تا 1,000,000؛ API admitted request/s؛ allocation | required؛ بدون default؛ min فقط در scope و الگوریتم یکسان | token-bucket با refill پیوسته و هزینه یک token برای هر attempt پذیرفته‌شده؛ PEP/limiter اعمال می‌کند |
| Burst | integer مثبت؛ token-bucket capacity؛ allocation | required؛ بدون default؛ min در scope همسان | ظرفیت مستقل bucket؛ `TPS + burst` فرمول سقف این profile نیست |
| Quota | integer 0..MAX_SAFE_INTEGER؛ admitted request؛ ماه تقویمی UTC | required؛ بدون default؛ min در scope/period همسان | quota صفر نامحدود نیست؛ پذیرش دوره بیرون PDP است |
| Zone | ID array غیرخالی؛ binding مورد اعتماد اجرا | required؛ بدون default؛ intersection | zone request از Gateway/binding معتبر، سپس PDP |
| Time / status | canonical UTC timestamp؛ `[validFrom,validTo)`؛ Active/Suspended/Ended | required؛ بدون default؛ intersection بازه‌ها | effectiveAt آینده، suspension و expiry اجازه تازه نمی‌دهند |

در این بسته merge اقتصادی یا محاسبه نرخ انجام نمی‌شود. adapter فقط مقدار مؤثر از قالب مصوب را دریافت می‌کند؛ کوچک‌ترین سقف سخت فقط برای واحد، scope، meter و الگوریتم همسان معنا دارد. scopeهای مشترک و زیرسقف‌ها نیازمند admission هم‌زمان همه محدودیت‌ها هستند؛ این slice فقط یک allocation دارد. concurrency، budget، currency، payout و پارامتر ناشناخته به مدل اضافه نشده‌اند. نبود پارامتر لازم یا وجود پارامتر پشتیبانی‌نشده باعث رد انتشار می‌شود و نامحدود تفسیر نمی‌شود. pricingReference فقط مرجع opaque نسخه قیمت است؛ sample-price-reference هیچ نرخ واقعی تعیین نمی‌کند.

## تصمیم و مرز اعتماد

فقط این conjunction می‌تواند Permit بسازد:

```text
identity/client/audience/scope
AND active consumer tenant + bound resource
AND active same-subject membership
AND active/effective contract + purchased action
AND explicit same-subject/consumer/product/action grant + eligible assigned role
AND allowed environment / operationGroup / zone
AND matching current contract/policy versions + fresh PIP evidence
```

سورس فعلی simulator، manual grant و Permit pattern را با OR جمع می‌کند و entitlement را نمی‌خواند؛ این evaluator نمونه برای خرید قراردادی، AND فوق را حفظ می‌کند. Template، policy ID/version و exact Deny action مصوب هستند؛ کد دلخواه یا expression در قرارداد اجرا نمی‌شود.

| Decision | معنای نمونه | رفتار PEP |
| --- | --- | --- |
| Permit | تمام شروط AND برقرار | فقط پس از هر دو obligation و پیش از validUntil |
| Deny | explicit Deny یا شرط معلومِ نامجاز | توقف |
| NotApplicable | محصول خارج target همین policy | توقف؛ PEP این نتیجه را اجازه پیش‌فرض نمی‌کند |
| Indeterminate | projection/context نامعتبر، attribute لازم مفقود، نسخه/freshness نامعتبر | توقف |

Explicit Deny با target/action معتبر حتی همراه خطای attribute دیگر حفظ می‌شود. این پیاده‌سازی، ترکیب کامل nested policyها و extended Indeterminateهای XACML را اجرا نمی‌کند. نقص ساختار context قبل از شروط معمولی به Indeterminate می‌رسد؛ Permitهای مستقل با OR تولید نمی‌شوند.

schema مربوط به Permit دقیقاً یک obligation از هر یک از دو ID زیر را لازم می‌داند:

- `urn:fanasa:obligation:admit-allocation:1`: PEP باید نرخ و quota همین allocation را در store مشترک و اتمیک بپذیرد، سپس forward کند.
- `urn:fanasa:obligation:resource-tenant:1`: backend باید resource/data را برای consumer/product/environment/action معتبر کنترل کند.

Obligation ناشناخته، تکراری، مخدوش، اجرا‌نشده یا deadline منقضی در helper نمونه PEP اجازه نمی‌دهد. `pepCanExecute` فقط proof-list مصنوعی آزمون را می‌سنجد؛ انجام واقعی admission یا کنترل داده را ثابت نمی‌کند. PEP عملیاتی باید نتیجه adapter مورد اعتماد همان درخواست را bind کند، همه نسخه‌ها را بازسنجی کند و completion را از مشتری نپذیرد. HTTP 200ِ PDP اجازه اجرا نیست. PDP شمارنده، audit، budget، usage، ledger یا grant نمی‌نویسد.

`environment.now` از ساعت سرور، zone از execution binding، identity از token validation و membership/grant/نسخه‌ها از PIP معتبر تهیه می‌شوند. این sample هیچ token، producer signature یا PIP شبکه را احراز نمی‌کند؛ boolهای fixture ادعای معتبر بودن هویت واقعی نیستند. `validUntil` کوچک‌ترین انتهای قرارداد/عضویت/grant/evidence و حداکثر ۶۰ ثانیه پس از evaluation است. cache/invalidation یا target قطع ۶۰ ثانیه‌ای در محیط واقعی پیاده نشده است؛ نسخه جاری باید در adapter تأیید شود.

## allocation و ترتیب event

Scope canonical فقط از allocation مرجع ساخته می‌شود؛ IDها lowercase ASCII و فاقد delimiter هستند، arrayها sort/unique می‌شوند و projection غیرمرتب رد می‌شود:

```text
tenant=tenant-b;products=club;environments=development;groups=reporting
fanasa:allocation:sample-allocation-club-b:<canonicalScope>:rate
fanasa:allocation:sample-allocation-club-b:<canonicalScope>:quota:2026-10
```

route، replica، requestId و contractVersion وارد کلید شمارنده نمی‌شوند. چند route از همین allocation یک کلید دارند. `productIds/environments/operationGroups` فقط اعضای scope تخصیص‌یافته‌اند؛ افزودن route کلید تازه نمی‌سازد. quota month از clock معتبر UTC و دوره مصوب به limiter داده می‌شود. افزایش limit یا amendment، allocation را عوض یا شمارنده را reset نمی‌کند. نمونه تغییر scope/allocation در همان subscription را رد می‌کند؛ reallocation/reset باید event تجاری صریح و مسیر پذیرش مستقل داشته باشد.

`projectEvent` snapshot کاملِ نگاشت‌شده را از producer از قبل احرازشده می‌پذیرد؛ price/business schema را نگاشت نمی‌کند. Fingerprint canonical کل envelope، receipt تکراری همسان را بی‌اثر و payload متعارض را conflict می‌کند؛ eventId تازه برای snapshot همسان نیز receipt می‌گیرد. aggregateVersion با contractVersion برابر است؛ نسخه پایین‌تر stale و نسخه برابر متعارض conflict است. snapshot کامل نسخه بالاتر می‌تواند از gap عبور کند؛ این رفتار برای eventهای delta مجاز نیست. Timestamp جای sequence نیست؛ suspension فوری نسخه بالاتر، amendment آینده را حتی با effectiveAt زودتر جایگزین می‌کند. suspension نسخه بالاتر را نگه می‌دارد؛ replay نسخه Active قدیمی آن را باز نمی‌کند. Ended برای همین subscription نهایی است و effectiveAt برابر/بعد از validTo برای snapshot نهایی مجاز است. Future-effective snapshot در نمونه بلافاصله جای current را می‌گیرد و تا effectiveAt اجازه نمی‌دهد؛ حفظ Active قبلی تا زمان آینده به تاریخچه زمان‌بندی‌شده در integration نیاز دارد.

State و receipts در حافظه و immutable هستند. atomic persist inbox/projection، تاریخچه، outbox، invalidation، دریافت هم‌زمان، recovery و published/acknowledged state در wiring پیشنهاد شده‌اند؛ این نمونه هیچ‌کدام را اجرا نمی‌کند.

## حد profile

این بسته چهار نتیجه و اولویت explicit Deny و obligations را با الهام از [OASIS XACML 3.0 + Errata 01، بخش 7.2/7.18 و Appendix C.2](https://docs.oasis-open.org/xacml/3.0/errata01/os/xacml-3.0-core-spec-errata01-os-complete.html) استفاده می‌کند. schemaهای حاضر DTO داخلی Fanasa هستند. [JSON Profile 1.1](https://docs.oasis-open.org/xacml/xacml-json-http/v1.1/os/xacml-json-http-v1.1-os.html) و [REST Profile 1.1](https://docs.oasis-open.org/xacml/xacml-rest/v1.1/os/xacml-rest-v1.1-os.html) هدف adapter آینده‌اند؛ wrapper استاندارد یا endpoint آن‌ها در این بسته اجرا نشده است.

| Supported در این sample | Unsupported / نیازمند پذیرش آینده |
| --- | --- |
| exact product/action target، role eligibility و binding واحد | arbitrary XML/XPath/functions، nested PolicySet، RBAC profile interoperability |
| AND شروط بالا، explicit deny precedence، چهار Decision | ترکیب عمومی deny-overrides با extended error effects یا الگوریتم دیگر |
| دو obligation شناخته‌شده و gate fail-closed | اجرای واقعی obligations، limiter/Gateway/backend/token validation |
| schema 1.0.0، timestamp واقعی UTC، حدود و canonical scope | همه keywordهای JSON Schema یا تأیید conformance validator عمومی |
| snapshot replay/order/suspend/end آفلاین | lifecycle تجاری/قیمت/امضای producer، persistence/worker، deployment reconciliation |

schema version و profile به 1.0.0 / fanasa.contract-policy/1 pin شده‌اند. تغییر breaking، schema/profile جدید و migration آشکار می‌خواهد؛ فیلد ناشناخته در نسخه فعلی silently ignored نمی‌شود. ادغام shared runtime پس از reconciliation سورس/artifact و تأیید نگاشت با مالک قرارداد، در PCC موجود و با پذیرش محصول واقعی انجام می‌شود.
