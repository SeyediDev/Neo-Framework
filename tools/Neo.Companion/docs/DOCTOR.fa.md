# Neo Doctor: تشخیص DI و Telemetry

Doctor کد C# و کلیدهای مشخص تنظیمات برنامه را بررسی می‌کند و برای هر مورد مشکوک، کد تشخیص، مسیر فایل، شاهد و پیشنهاد بررسی می‌دهد. نسخهٔ اول تحلیل ایستای syntax دارد؛ برنامه را اجرا نمی‌کند و سلامت زمان اجرا را تضمین نمی‌کند.

## استفاده

در تنظیم MCP، `NEO_PROJECT_ROOT` را به ریشهٔ **یک برنامهٔ مصرف‌کنندهٔ نئو** بده. سپس از دستیار بخواه:

> با neo-doctor بررسی کن چرا سرویس سفارش با وجود TelemetryAttribute هیچ Span تولید نمی‌کند. اول علت را با شاهد مشخص کن و بعد اصلاح را با تست بررسی کن.

ابزار `neo_diagnose_project` آرگومان `configurationSection` دارد. مقدار پیش‌فرض `TelemetryOptions` است؛ برای تنظیمات ریشه مقدار خالی و برای بخش تو‌در‌تو مثلاً `Observability:Telemetry` بده. این مقدار باید با بخش واقعاً bindشده در برنامه هماهنگ باشد.

## گزارش را چطور بخوانیم؟

| کد | چیزی که بررسی می‌شود |
|---|---|
| NEO-TEL001 | ثبت مستقیم DI برای سرویسی که متد دارای attribute دارد |
| NEO-DI001 | نبودن ثبتِ قابل‌شناسایی برای یکی از وابستگی‌های پروکسی |
| NEO-TEL002 | ساخت مستقیم implementation با new در کنار ثبت پروکسی |
| NEO-TEL003 | نبودن شاهد شناخته‌شده برای ثبت listener تریس |
| NEO-CONFIG001 | نام خالی برنامه یا شکل نامعتبر آدرس OTLP در بخش انتخاب‌شده |
| NEO-SCAN001/002 | فایل C# یا JSON که تحلیل آن کامل نشده است |

این‌ها «موارد نیازمند بررسی» هستند. مثلاً ثبت IRequesterUser می‌تواند داخل یک extension در پکیج دیگری باشد؛ Doctor نباید نبود آن در سورس فعلی را خطای قطعی اعلام کند. ساخت مستقیم یک کلاس هم ممکن است عمداً برای تحویل آن به یک proxy factory انجام شده باشد.

وضعیت `review-required` یعنی اسکن در محدودهٔ پشتیبانی‌شده انجام شده، اما اعتبارسنجی runtime باقی است. `incomplete` یعنی بخشی از فایل‌ها قابل تحلیل نبوده‌اند. فهرست خالی findings هم به‌تنهایی به معنی سالم‌بودن برنامه نیست.

شمارهٔ خط C# یک‌مبناست. برای JSON از `jsonPointer` استفاده کن؛ خط ۱ صرفاً فایل را مشخص می‌کند. مقدار تنظیمات، متن کامل سورس، connection string و پیام خطای parser در خروجی برگردانده نمی‌شود.

## نمونه‌های آموزشی و تست

در [DoctorCases](../samples/DoctorCases/README.md) چهار حالت وجود دارد: ثبت مستقیم بدون Span، وابستگیِ ثبت‌نشده، تنظیمات نامعتبر و ثبت صحیح. تست‌ها سه سرویس را واقعاً اجرا یا resolve می‌کنند و راه‌اندازی exporter با تنظیمات نامعتبر را نیز بررسی می‌کنند.

از ریشهٔ ریپازیتوری:

```powershell
dotnet test tools/Neo.Companion/tests/Neo.Companion.Tests/Neo.Companion.Tests.csproj --filter FullyQualifiedName~Doctor
```

برای آزمون خود پروتکل پس از publish:

```powershell
python tools/Neo.Companion/scripts/smoke_mcp.py --server-dll tools/Neo.Companion/artifacts/mcp/Neo.Companion.Mcp.dll --project-root tools/Neo.Companion/samples/DoctorCases/DirectRegistration --doctor-expect-code NEO-TEL001
```

## محدودهٔ نسخهٔ اول

نام typeها و extensionها از syntax استخراج می‌شود؛ symbol resolution، اجرای MSBuild، ترتیب ثبت DI و شرط‌های runtime تحلیل نمی‌شوند. شرط‌های پیش‌پردازنده و C# نامعتبر باعث ردشدن تحلیل همان فایل می‌شوند. ثبت‌های خارجی، aliasها، attribute ارث‌بری‌شده و implicit new نیازمند بررسی جداگانه‌اند. مشاهدهٔ wrapper دستی، هشدار ثبت مستقیم را حذف می‌کند؛ این به معنی اثبات پوشش تمام متدها نیست.

فایل‌های generated و پوشه‌های خروجی نادیده گرفته می‌شوند. لینک‌ها دنبال نمی‌شوند و فایل‌های بزرگ یا غیرقابل‌تحلیل در پوشش گزارش مشخص می‌شوند. سقف‌ها: ۵۰۰۰ ورودی، عمق ۲۰ پوشه، ۵۱۲ کیلوبایت برای هر فایل، ۸ مگابایت در مجموع و ۱۰۰ یافته. عبور از سقف کلی، خطای ابزار می‌دهد.

نام منبع و endpoint نهاییِ محیط اجرا، ترتیب فایل‌های appsettings و overrideهای محیطی تعیین نمی‌شوند. برای اثبات رفع ایراد باید resolve شدن سرویس یا Span واقعی را بررسی کرد. راهنمای جزئیات ابزارگذاری در [Telemetry](TELEMETRY.fa.md) است.
