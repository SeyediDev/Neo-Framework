# تعریف منبع CRUD و همزمانی

این قابلیت اختیاری برای داده‌های مدیریتی نئو است. قرارداد قدیمی `GenericCrudControllerBase<TDto,TEntity,TKey>` حفظ شده است. اصلاح صفحه‌بندی روی همان مسیر قدیمی هم اعمال می‌شود. وضعیت زندهٔ مراحل `NEO-CRUD-101` تا `NEO-CRUD-104` و شواهد آن‌ها در WorkManagement است؛ [مشخصات پذیرش](crud-resource-backlog.json) در ریپازیتوری نگهداری می‌شود.

## قرارداد Application

`CrudDefinition<TCreate,TUpdate,TRead,TEntity,TKey>` محل تعریف عملیات فعال، policy هر عملیات، فیلترها و ترتیب‌های مجاز، نگاشت صریح ورودی‌ها و خروجی، scope رکوردها و روش همزمانی است. DTOهای ایجاد و ویرایش جدا هستند. شناسه و Version در envelope پاسخ قرار می‌گیرند و نگاشت خودکار تمام فیلدهای Entity انجام نمی‌شود. قواعد دامنه را در متدهای Create/Update تعریف یا فراخوانی کنید؛ این قابلیت برای عملیات دامنهٔ پیچیده مانند پرداخت جای handler اختصاصی را نمی‌گیرد.

برای هر عملیات فعال، policy را مشخص کنید. مقدار null یعنی اجازهٔ صریح دسترسی ناشناس؛ نبود مقدار به معنی تنظیم ناقص است. Scope باید محدودیت tenant/مالکیت را روی خواندن، ویرایش و حذف اعمال کند؛ هنگام ایجاد نیز tenant و فیلدهای مدیریتی را از هویت معتبر سمت سرور بگیرید. فراخوانی مستقیم سرویس Application داخل برنامه، جای کنترل مجوز ورودی HTTP را نمی‌گیرد.

Query، حداکثر ۲۰۰ ردیف و یک ردیف اضافی برای HasNext می‌خواند. کلید Entity معیار نهایی مرتب‌سازی است؛ sort و filter فقط از فهرست تعریف‌شده پذیرفته می‌شوند. حداکثر ده فیلتر و ۲۵۶ نویسه برای هر مقدار مجاز است. پارامترهای ورودی به نام ستون یا SQL خام تبدیل نمی‌شوند.

## خوش‌بینانه و بدبینانه

| روش | رفتار | کاربرد |
|---|---|---|
| Optimistic، پیش‌فرض | Version رکورد در شرط UPDATE/DELETE قرار می‌گیرد؛ تغییر هم‌زمان تعارض ایجاد می‌کند | بیشتر فرم‌های مدیریتی |
| Pessimistic | ابتدا SQL Server رکورد را با UPDLOCK/HOLDLOCK تا پایان تراکنش قفل می‌کند؛ سپس Version هم کنترل می‌شود | تغییرهایی که نیازمند قفل پیش از محاسبه و ذخیره هستند |

Entity باید `IConcurrencyVersion` را پیاده کند. در مدل EF از `model.ConfigureNeoConcurrency()` و در options از `AddInterceptors(new NeoConcurrencyInterceptor())` استفاده کنید. اگر interceptor رویداد دامنه نیز دارید، interceptor نسخه را بعد از آن قرار دهید تا تغییرات ایجادشده توسط handlerها هم دیده شوند. interceptor، Version را برای insert و update تولید می‌کند؛ در نتیجه ذخیره‌های EF خارج از CRUD هم قابل کنترل‌اند. ExecuteUpdate، SQL خام و نویسنده‌های خارجی interceptor را دور می‌زنند؛ آن مسیرها باید شرط نسخه و تغییر token را صریح رعایت کنند.

ورودی Update/Delete باید ExpectedVersion خوانده‌شده را ارسال کند. حتی در حالت بدبینانه، نسخهٔ قدیمی فرم پذیرفته نمی‌شود. قفل فقط طی پردازش یک درخواست نگه داشته می‌شود؛ زمان فکرکردن کاربر بخشی از تراکنش نیست. تعارض نسخه با کد `stale_version` و شلوغی/timeout قفل با `resource_busy` مشخص می‌شود. retry خودکار روی نسخهٔ جدید، تغییر کاربر دیگر را بازنویسی می‌کند؛ ابتدا رکورد را دوباره بخوانید و تصمیم کسب‌وکار را بگیرید.

`SqlServerRowLock.AcquireAsync<TEntity>` مستقل از Controller هم قابل استفاده است: DbContext باید تراکنش فعال، جدول معمولی بدون نگاشت ارث‌بری و کلید اصلی تک‌ستونی داشته باشد. نام جدول و ستون از metadata و quoting provider، و مقدار کلید از پارامتر SQL می‌آید. قفل داخل SQL Server است و بین پردازش‌ها عمل می‌کند؛ قفل حافظه‌ای یا Redis جایگزین آن نشده است. SQL Server می‌تواند قفل را به سطح گسترده‌تر ارتقا دهد؛ این API تضمین انحصار فقط یک قفل فیزیکی row-level نمی‌دهد.

LockWait بین ۱ تا ۳۰ ثانیه و پیش‌فرض ۳ ثانیه است؛ به timeout دستور SQL با گردکردن رو به بالا به ثانیه تبدیل می‌شود. cancellation به SqlClient می‌رسد. rollback/commit قفل را آزاد می‌کند. SQLite فقط برای حالت خوش‌بینانه و تست تراکنش پشتیبانی می‌شود؛ حالت بدبینانه روی آن صریحاً رد می‌شود. برای عملیات چندرکوردی پیچیده، ترتیب قفل‌گیری و invariant تراکنش را در سرویس اختصاصی تعریف کنید؛ CRUD یک رکورد مانع همهٔ انواع write-skew نیست.

## تراکنش موجودیت، ترجمه و Outbox

از `AddNeoCrudResource<TContext,TDefinition,TCreate,TUpdate,TRead,TEntity,TKey>()` استفاده کنید. هر mutation به scope/DbContext تازه نیاز دارد و تراکنش خودش را مدیریت می‌کند. context دارای tracked entity یا تراکنش بیرونی رد می‌شود؛ اتصال این سرویس به یک واحد کار بزرگ‌تر باید با handler اختصاصی انجام شود. retry خودکار EF برای این context فعال نباشد.

`ICrudTransactionParticipant<TContext,TEntity>` تغییرات تکمیلی مانند ترجمه و Outbox را پس از save موجودیت و پیش از commit آماده می‌کند. context همان تراکنش به participant داده می‌شود؛ حتی اگر participant یک save انجام دهد و سپس خطا رخ دهد، کل تراکنش rollback می‌شود. handler دامنه هم می‌تواند پیام را در Outbox همین context ثبت کند. هیچ تماس HTTP، پرداخت یا ایمیلی داخل participant انجام ندهید؛ اثر خارجی با rollback دیتابیس برنمی‌گردد.

در صورت شکست، tracker پاک می‌شود و درخواست خطا می‌گیرد؛ instanceهای Entity که caller قبلاً نگه داشته ممکن است همچنان تغییرات حافظه را داشته باشند. آن‌ها را نتیجهٔ commit تلقی نکنید. این مسیر، رفتار قدیمی ذخیرهٔ جداگانهٔ CultureTerm را به‌صورت پنهان تغییر نمی‌دهد؛ نمونهٔ جدید، ترجمهٔ دارای کلید Guid را در جدول برنامه و تراکنش مشترک نشان می‌دهد.

## ارتقای دیتابیس

Version از نوع Guid، required و concurrency token است. migration برنامه باید ستون و backfill رکوردهای موجود را انجام دهد؛ صرف ثبت سرویس یا اجرای Doctor دیتابیس را migrate نمی‌کند. کلاینت باید Version پاسخ را نگه دارد و در ویرایش/حذف بعدی ارسال کند. قبل از فعال‌کردن قرارداد جدید، سایر نویسنده‌های همان جدول را نیز با این قاعده هماهنگ کنید.

مراجع طراحی: [همزمانی EF Core](https://learn.microsoft.com/en-us/ef/core/saving/concurrency) و [قفل‌های SQL Server](https://learn.microsoft.com/en-us/sql/t-sql/queries/hints-transact-sql-table). سازگاری پیاده‌سازی با نسخه‌های همین ریپازیتوری در تست‌های SQLite و SQL Server بررسی می‌شود.
