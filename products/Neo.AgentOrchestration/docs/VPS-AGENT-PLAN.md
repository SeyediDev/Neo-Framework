# اجرای ایجنت روی VPS از پنل فن آسا

## پیشرفت پیاده‌سازی — ۲۰۲۶-۱۰-۰۹

اتصال‌های native هر دو ایجنت و [هستهٔ ثبت پایدار اجرا](GATEWAY-JOURNAL.md)
پیاده شده‌اند. میزبان عملیاتی gateway، اتصال پایدار به worker موجود، محیط
اجرای ایزولهٔ واقعی، ingestion مصرف و پایلوت مدل هنوز تکمیل نشده‌اند.
این مرحله به معنی نصب روی VPS یا فعال‌شدن اجرای خودکار نیست.

این سند طرح اجرایی است، نه ادعای نصب یا یک بک‌لاگ موازی. وضعیت، مالکیت و
پذیرش کارها باید در دیتابیس عملیاتی مدیریت کار ثبت شود. وضعیت جاری از API
خوانده شود؛ جدول بسته‌های پیشنهادی پایین سند به‌خودی‌خود رکورد تسک محسوب نمی‌شود.

## تصمیم تأییدشده — ۲۰۲۶-۱۰-۰۹

کاربر استفاده از **Hermes و OpenCode با هم** را تأیید کرد. هارنس وابسته به برند
یک مدل نباشد: OpenCode مسیر پیش‌فرض پیشنهادی coding و Hermes مسیر automation
و کار عمومی است؛ انتخاب از پروفایل مجاز و نوع کار، نه تحلیل آزاد متن تسک توسط
مدل. هر دو پشت gateway مشترک و گردش‌کار موجود قرار می‌گیرند. این تقسیم کار
تصمیم معماری است، نه ادعای برتری حاصل از بنچمارک. پذیرش پس از اجرای واقعی.

Hermes جایگزین ارکستریتور فن آسا نیست؛ kanban و cron داخلی آن مرجع دومِ
تسک/زمان‌بندی نمی‌شوند. زنجیره اجباری Hermes→OpenCode برای همه کارها نداریم؛
handoff تنها در فلو مجاز، با run جدید، مالکیت، context محدود و بودجه مشخص.
حافظه/skills/profile بین تننت‌ها مشترک نشود؛ session key به‌تنهایی sandbox
امن ایجاد نمی‌کند. Codex و Aider همچنان گزینه‌های آینده‌اند، نه نصب فعال.

| گزینه | شاهد رسمی | تناسب با نیاز پنل |
| --- | --- | --- |
| OpenCode | HTTP/OpenAPI، نشست، SSE، abort و درخواست مجوز؛ providerهای متعدد، Ollama و OpenRouter | مسیر coding؛ مزیت ابزارهای مخزن و زبان، نیازمند اجرای واقعی و ارزیابی |
| Hermes | API اجرای async، idempotency، وضعیت/رویداد/توقف، skills و حافظه | مسیر automation/general؛ قابلیت‌ها در پروفایل و محیط مستقل محدود شوند |
| Codex CLI | اجرای غیرتعاملی و JSON؛ ورود رسمی headless یا API key | adapter اختیاری برای حساب مجاز کاربر؛ نه الزام محصول |
| Aider | اجرای اسکریپتی CLI و اتصال به providerهای مختلف | گزینهٔ سبک برای اصلاح محدود؛ نه جایگزین گردش‌کار و کنترل اجرای محصول |

## منابع موجود و انتخاب مدل

بازرسی read-only سرور: ۴ CPU، حدود ۷٫۸ GiB RAM؛ حدود ۱٫۸ GiB available در زمان
بررسی، چند سرویس وب، Keycloak، SQL، PostgreSQL و Ollama فعال. ابزار VGA مجازی
مشاهده شد؛ GPU محاسباتی قابل استفاده تأیید نشده است. مدل‌های موجود Ollama:
tinyllama، phi3:3.8b و nomic-embed-text. مدل embedding عامل کدنویسی نیست؛ وجود
دو مدل کوچک دیگر نیز شاهد کیفیت کافی برای تغییرات خودکار این محصول نیست.

پایلوت: مدل API با tool-calling و کیفیت کدنویسی قابل‌آزمون؛ یک اجرای همزمان،
سقف زمانی/توکن، و محدودیت CPU/RAM. سقف منابع پس از اندازه‌گیری build/test
تنظیم شود تا سرویس‌های موجود تحت فشار قرار نگیرند. رایگان‌بودن نرم‌افزار
ایجنت با رایگان‌بودن inference متفاوت است؛ free tier محدود، متغیر و بدون
تضمین ظرفیت است. مدل رایگان فقط پس از بررسی شرایط، حریم خصوصی و موفقیت
آزمون انتخاب شود. بدون اجازه، کد خصوصی برای provider جایگزین ارسال نشود.
Ollama روی همین VPS فعلاً فقط برای آزمون سبک؛ اجرای مدل بزرگ روی سرور جدا
یا سرویس GPU در آینده، بدون تغییر پنل.

## مسیر اجرای واحد؛ بدون ساخت صف و کانبان دوم

پنل → مجوز execute و شروع run → Outbox/Hangfire موجود → gateway فن آسا →
محیط مجزای کار → adapter ایجنت → نتیجه و گزارش مصرف → Review → گیت مستقل.

در حال حاضر پروتکل HTTP و callback در [HARNESS.md](HARNESS.md)، اجرای durable
در [RUNS.md](RUNS.md) و زیربنای ACP در [ACP.md](ACP.md) وجود دارد؛ این‌ها به
معنی نصب و اتصال زندهٔ یک ایجنت نیستند. API محصول dispatcher نیست. gateway
باید پروتکل محصول را به API ایجنت تبدیل کند؛ هیچ‌کدام مستقیماً آن را نمی‌فهمند.
قرارداد و کلاینت‌های native در [NATIVE-AGENTS.md](NATIVE-AGENTS.md) تعریف شده‌اند؛
کلاینت با gateway durable، sandbox یا اتصال زنده یکی نیست. نسخه پروتکل موجود
و callback تغییر نکرده و هیچ پروفایل یا worker به‌طور ضمنی فعال نمی‌شود.

- از شناسهٔ run برای نگاشت پایدار session، repo، commit و worktree استفاده شود.
  پذیرش 202 فقط پس از ذخیرهٔ durable؛ retry همان اجرا را پیدا کند، نه اجرای جدید.
  Hermes کلید native را ۲۴ ساعت پس از آخرین وضعیت نگه می‌دارد؛ نگاشت فن آسا
  باید طولانی‌تر حفظ شود و پس از انقضا اجرای نامطمئن را دوباره شروع نکند.
  OpenCode prepare/session باید پیش از prompt ذخیره شود؛ messageID ثابت
  تضمین exactly-once نیست. از دست رفتن پاسخ write نیازمند reconciliation است.
- هر اجرا محیط مجزا، کاربر non-root و branch/worktree خودش را داشته باشد؛
  مرز سازمان/پروژه در workspace، secrets، artifacts و دسترسی مخزن حفظ شود.
- متن تسک ورودی غیرقابل‌اعتماد است. فقط repo و base commit مجاز و دستورهای
  تأییدشده قابل استفاده باشند. مسیرهای میزبان، Docker socket، اطلاعات SQL/SSO،
  کلید root و فایل‌های اعتبار محلی به محیط ایجنت mount نشوند.
- شبکه و حجم خروجی محدود؛ هیچ endpoint خام ایجنت به اینترنت عرضه نشود.
  gateway فقط از اتصال خصوصی تأییدشده استفاده کند؛ احراز هویت و secrets آن
  با دسترسی پنل یا کلید provider یکی نباشد.
- پیام permission از ایجنت به NeedsInput/انتظار تأیید در پنل نگاشت شود؛
  answer عمومی «همه را مجاز کن» یا اجرای خودکار دستورات مبهم ممنوع.
- توقف/timeout باید وضعیت فرایند واقعی را reconcile کند؛ قطع شبکه به معنی
  توقف قطعی یا شکست اجرا نیست. پس از restart، شناسهٔ session بازیابی شود.
- موفقیت فقط با diff و شواهد واقعی build/test؛ خروجی به Review برود، نه Done
  یا deploy خودکار. publish/merge/deploy نیازمند اختیار و گیت جداگانه است.
- زمان صف، زمان اجرای واقعی و زمان فعال تسک از هم جدا نمایش داده شوند.
  مصرف provider به‌صورت delta با شناسهٔ پایدار گزارش شود؛ snapshotهای cumulative
  دوباره جمع نشوند. input/output مبنای total و cache/reasoning زیرمجموعه‌اند.
  نبود گزارش مصرف = نامعلوم، نه صفر. برآورد بودجه مستقل از مصرف و پیشرفت است.
- context اولیه نسخهٔ bounded قرارداد v2 باشد؛ نیاز به تاریخچهٔ حذف‌شده با
  read محدود به همان task تأمین شود. خلاصه/لاگ‌ها پالایش و حجمشان محدود شود.

## کلید و حساب

کلید مدل فقط در secret store اپراتور و به‌صورت reference در تنظیمات پنل؛
نه در تسک، گیت، log، آرگومان CLI یا artifact. برای SaaS، حساب شخصی یک نفر
اعتبار مشترک همهٔ تننت‌ها نشود. credential و محدودیت مصرف به tenant/project
بسته شود. ورود Codex اگر انتخاب شد از روش رسمی با اقدام خود کاربر؛ کپی
اعتبار این چت یا خواندن auth cache انجام نمی‌شود. قابلیت OAuth هر provider
پیش از فعال‌سازی با شرایط همان سرویس بررسی شود.

## ترتیب پیشنهادی بسته‌های کار و معیار پذیرش

این جدول طرح intake بعدی است، نه فهرست کارهای claim‌شده. ابتدا جست‌وجوی
تسک‌های موجود و مالک آنها، سپس ایجاد/اتصال رکوردهای فاقد معادل در همان پروژه.

| ترتیب | دامنه / نقش پیشنهادی | خروجی قابل پذیرش |
| --- | --- | --- |
| ۱ | operations / امنیت و زیرساخت | حساب non-root، runtime pin‌شده، health، آزمون محدودیت منابع و عدم دسترسی به سرویس‌ها و اسرار میزبان |
| ۲ | harness / backend | دو native adapter و سپس gateway واحد با ذخیرهٔ نگاشت، پذیرش durable و آزمون duplicate/changed-payload/restart |
| ۳ | repositories / زیرساخت مخزن | repo allowlist، revision ثابت، محیط مجزا و artifact diff؛ بدون push خودکار |
| ۴ | metering / backend | ingestion معتبر، delta idempotent، تخصیص به run، سقف مصرف/timeout و reconciliation |
| ۵ | web / پنل | انتخاب agent/model، صف و وضعیت زنده، log محدود، درخواست مجوز، توقف و نمایش مصرف |
| ۶ | quality / بازبینی مستقل | یک تسک کوچک واقعی از کانبان تا Review؛ diff، build/test و شواهد قابل مشاهده |
| ۷ | reliability / زیرساخت | بازیابی قطع شبکه/سرور، لغو، fairness و آزمون عدم نشت بین دو تننت |

بودجهٔ اولیهٔ پایلوت: حدود **۳ تا ۵ روز کاری توسعه و آزمون**، مشروط به دسترسی
مخزن و provider و عدم نیاز به توسعهٔ زیرساخت جداگانهٔ secrets/sandbox.
این تخمین تقویمی تضمین نیست و پس از spike بستهٔ ۱ و ۲ بازبرآورد می‌شود.
برآورد توکن بدون تعیین مدل، سقف context و تعداد retry قابل اتکا نیست؛ قبل از
اجرا باید بودجهٔ صریح تنظیم و با پایلوت مصرف واقعی اندازه‌گیری شود، نه عددسازی.
هیچ provider، دسترسی جدید، جاب یا اجرای مدل با نوشتن این سند فعال نشده است.
