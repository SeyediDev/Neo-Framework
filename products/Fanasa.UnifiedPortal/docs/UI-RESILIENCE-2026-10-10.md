# اصلاحات محدود پنجره واحد — ۲۰۲۶-۱۰-۱۰

مالک محدوده: چت پنجره واحد `01a0feb9-0662-7141-95e5-7faaaa9ba45c`، برنچ `develop`.
درخواست مستقیم کاربر برای ادامه چت‌های منتظر در چت هماهنگ‌کننده بررسی شد؛
محدوده هماهنگی فقط محصول `Fanasa.UnifiedPortal` است.

فایل‌های اجرایی این مرحله: `Pages/Shared/_Layout.cshtml`، `wwwroot/portal.js`
و `wwwroot/portal.css`؛ آزمون و سند فقط در همین محصول اضافه می‌شوند.
تغییرات موجود دیگران، از جمله پوشه `Properties`، حفظ و از کامیت کنار گذاشته می‌شوند.
این یادداشت گزارش کار و شواهد است، نه برد عملیاتی موازی یا رزرو تسک در Neo.
MCP عملیاتی برد و credential آن در این نشست موجود نیست؛ ثبت شواهد در برد انجام نشده است.

## پذیرش موردنظر

- ناوبری داخل صفحه بدون بارگذاری سند جدید؛ حفظ انتخاب سازمان، جست‌وجو و فیلتر.
- سقف انتظار ۵۰ ثانیه برای کل پاسخ فضای کار، شامل خواندن body؛ پیام timeout،
  آزادشدن کنترل‌ها و امکان تلاش مجدد؛ پاسخ دیررس یا درخواست قدیمی جای پاسخ جدید را نگیرد.
- نبود سرریز افقی در viewportهای کوچک ۳۲۰ و ۳۹۰ پیکسل، بدون مخفی‌کردن محتوا.
- حفظ آزمون‌های قرارداد، نشست موجود و رد سازمان خارج از دسترسی.

۵۰ ثانیه کمی بیشتر از سه درخواست متوالی ۱۵ثانیه‌ای سمت سرور است؛ timeout جدید
قرار نیست مجوز، داده یا سیاست مرکزی را تغییر دهد. تغییر نشانه‌های بصری برند،
ایجاد محصول یا grant، ورود به محصول نامجاز و تغییر Keycloak خارج از این مرحله است.

## نتایج اجرا

- اجرای Release پروژه `tests/Portal.Tests` موفق بود؛ ۴۹ بررسی قرارداد و PageModel
  پاس شدند. نسخه اصلاح‌شده Razor در این بیلد کامپایل شد.
- `node --test products/Fanasa.UnifiedPortal/tests/portal-client.test.cjs`:
  هر ۸ تست پاس شد. Node runner ابتدا به محدودیت spawn در sandbox برخورد کرد؛
  اجرای مجاز خارج sandbox و اصلاح هماهنگی promiseهای fixture نتیجه نهایی را داد.
  این تست‌ها رفتار script واقعی را با DOM کوچک آزمایشی بررسی می‌کنند، نه layout مرورگر.
- میزبان آزمایشی روی loopback `127.0.0.1:15190` با تنظیمات هویت آزمایشی نامعتبر
  و بدون ورود اجرا شد؛ هیچ حساب، مجوز یا سرویس هویت واقعی ایجاد نشد.
- چهار smoke check روی HTTP واقعی موفق بود: لینک‌های fragment-only در صفحه
  اصلی دارای پارامتر tenant، بازگشت لینک‌های صفحه Error به صفحه اصلی، پاسخ ناشناس
  `SignInRequired` با `no-store`، و سرو‌شدن JS حاوی deadline پنجاه‌ثانیه‌ای.
  درخواست اولیه با timeout پانزده‌ثانیه‌ای در startup کند منقضی شد؛ log میزبان
  پایان HTTP 200 همان درخواست را نشان داد و آزمون پس از گرم‌شدن موفق بود.
- ابزار مرورگر در این نوبت سه بار timeout داد. بنابراین کلیک و حفظ واقعی search/
  filter در مرورگر، اندازه‌گیری `scrollWidth` در نسخه اصلاح‌شده و پذیرش دیداری
  ۳۲۰/۳۹۰ پیکسل هنوز تأیید نشده‌اند. اصلاح CSS انجام شده، ولی موفقیت layout از
  صرف وجود media query یا آزمون Node نتیجه گرفته نمی‌شود.
- فایل‌ها و APIهای registry، SSO، grants و سایر محصولات تغییر نکردند. رنگ، نشان
  و فونت برند نیز حفظ شدند. این تغییر، schema اسکیل یا MCP را عوض نمی‌کند؛ README
  و دستور اجرای آزمون جدید همگام شدند.

## استقرار توسعه و ادامه بررسی

نسخه `61201cf4377ef6f28accd2104734e7c5c88545fc` روی VPS در محیط development
با اسکریپت موجود نصب شد؛ production، سرویس هویت و مرکز راهبری تغییر نکردند.
SHA256 بسته روی سرور با مقدار محلی برابر بود. انتقال اولیه SFTP بسته شد؛
انتقال SCP با `-O` و اعتبارسنجی سختگیرانه host key موفق شد.
سرویس `fanasa-unified-portal@development` فعال و release قبلی
`499ac1cd9ae4f619fb9e61ba03b6f267b5867e78` برای بازگشت حفظ شد.
پنج بررسی HTTPS موفق بود: سلامت، ناوبری صفحه اصلی، فضای کار ناشناس محافظت‌شده،
deadline در JS و media query موبایل در CSS.

در ادامه، آزمون HTTP جدید روی همان نسخه، ایراد مسیر `/Index` را بازتولید کرد:
منو alias صفحه اصلی را تشخیص نمی‌داد و به جای fragment، سند اصلی را دوباره باز می‌کرد.
تشخیص صفحه از هویت Razor (`/Index`) جای مقایسه رشته URL را گرفت؛ آزمون
`tests/Test-PortalHttp.ps1` مسیرهای `/`، `/Index`، `/index` و `/Error` را پوشش می‌دهد.
ابزار مرورگر و helper دیداری پس از بازیابی مجاز همچنان timeout دادند؛ پذیرش
دیداری و سناریوی نشست واقعی را نمی‌توان از این بررسی‌های HTTP نتیجه گرفت.

پس از اصلاح alias، اجرای Release پروژه آزمون دوباره با ۴۹ بررسی موفق تمام شد؛
هر ۸ تست Node نیز پاس شد. بیلد این مرحله کند بود، اما با exit code صفر تمام شد؛
تأخیر کامپایل به عنوان شکست یا نتیجه تست مرورگر گزارش نمی‌شود.
هشت بررسی HTTP روی میزبان محلی اصلاح‌شده پاس شدند، از جمله هر سه مسیر صفحه اصلی
و برگشت درست از Error. اولین درخواست محلی با سقف ۶۰ثانیه timeout شد؛ لاگ پایان
HTTP 200 آن را در حدود ۱۰۰ثانیه نشان داد و اجرای مجدد پس از warm-up موفق بود.
