# کاتالوگ سرویس‌های مراکز — ۱۲ اکتبر ۲۰۲۶

## تجربهٔ کاربر و مرز مجوز

فهرست سامانه‌های مجاز برای ورود، با فهرست سرویس‌های قابل معرفی یکی نیست.
پنجره واحد، متادیتای منتشرشدهٔ کاتالوگ مرکزی را در کارت هر یک از ۱۴ مرکز نشان
می‌دهد؛ نام و توضیح سرویس نیز در جست‌وجوی مراکز لحاظ می‌شود. آدرس مرکز ابر در
registry برابر `fanasa.cloud` و کلید دارایی نشان آن `fanasa-cloud` است.

- دارای مجوز معتبر در سازمان فعال: توضیحات، معرفی و ورود به سامانه.
- بدون مجوز: توضیحات، معرفی و لینک مرکزی درخواست دسترسی / خرید؛ بدون لینک ورود.
- نشست ناشناس، سازمان انتخاب‌نشده، عضویت لغوشده یا خطای مجوز: معرفی مستقل می‌ماند،
  اما مجوز ورود ساخته نمی‌شود. وضعیت دسترسی مشخص است.
- سرویس منتشرنشده: حتی اگر ثبت داخلی داشته باشد، در کاتالوگ معرفی نمایش داده نمی‌شود.
- مسیر درخواست هنوز منتشر نشده: پیام صریح نشان داده می‌شود؛ لینک سفارش حدس زده نمی‌شود.

دکمه درخواست، تنها ارجاع به جریان رسمی منتشرشده مرکزی است. Portal درخواست،
پرداخت، قرارداد، entitlement یا grant جدید ایجاد نمی‌کند. خرید یا تأیید درخواست
به‌تنهایی مجوز ورود نیست؛ پس از صدور مجوز مرکزی، تازه‌سازی همان پاسخ مجاز را می‌خواند.
محصول مقصد نیز باید مستقل از قابل‌دیدن‌بودن لینک، مجوز عملیات را اعمال کند.

## قرارداد adapter و وضعیت اتصال

`IServiceDiscoveryClient` از محصولات مجاز `IPlatformCatalogClient` مستقل است.
کلاینت سرویس با scope خواندنی محدود، metadata عمومی منتشرشده را می‌گیرد؛ subject
و tenant دلخواه به discovery فرستاده نمی‌شود. productId، key و center با پاسخ
محصولات مجاز سازمان مصرف‌کننده تطبیق می‌خورند. owner tenant با consumer اشتباه
گرفته نمی‌شود. URL ورود فقط از پاسخ مجاز محصولات گرفته می‌شود، نه metadata معرفی.

تنظیمات افزوده:

- `PlatformControlCenter__DiscoveryPath`: مسیر نسبی مصوب API زیر `/api/platform/`؛
  پیش‌فرض عمداً خالی است. تا اعلام endpoint واقعی از طرف مالک مرکز، متصل نیست.
- `PlatformControlCenter__DiscoveryScope`: scope خواندنی، پیش‌فرض `platform.catalog`؛
  استفاده از scope نوشتن registry یا client ادمین برای خواندن همه محصولات مجاز نیست.

قرارداد **پیشنهادی برای تطبیق توسط مالک مرکز**، نه ادعای API موجود:

```json
[
  {
    "productId": "11111111-1111-4111-8111-111111111111",
    "key": "published-service-key",
    "displayName": "نام سرویس منتشرشده",
    "center": "fanasa.rayan",
    "description": "شرح عمومی مورد تأیید ناشر",
    "detailsUrl": "https://catalog.example.test/services/published-service-key",
    "requestAccessUrl": "https://catalog.example.test/requests/published-service-key",
    "published": true
  }
]
```

شناسه باید همان Id محصول در API محصولات مجاز باشد. URL نمونه‌ها مقصد واقعی نیستند.
متادیتای خصوصی، repository، attributes، clients، credential و launchUrl در این DTO
وجود ندارند. فقط `published: true` نمایش داده می‌شود. مرکز ناشناخته، شناسه تکراری،
JSON نامعتبر یا نام/شرح ناقص خطا هستند، نه فهرست خالی موفق. پاسخ transport به
۲MiB و ۲۰۰۰ رکورد و کل دریافت به ۳۰ثانیه محدود است. هیچ pagination خاموش یا truncation
انجام نمی‌شود؛ کاتالوگ بزرگ‌تر نیازمند قرارداد صفحه‌بندی مصوب است.

کاتالوگ و workspace به صورت موازی دریافت می‌شوند. پاسخ شخصی no-store است؛
credentials فقط روی سرور می‌مانند. تغییر سازمان فوراً تمام لینک‌های ورود مراکز
را حذف می‌کند. پاسخ دیررس درخواست قبلی اجازه بازنویسی پاسخ جدید را ندارد.
کل دریافت مرورگر شامل body سقف ۵۰ثانیه دارد. UI خرید mock یا grant ساختگی در محصول وب نیست.

## مالکیت و تحویل

کار این چت فقط پنجره واحد است. تغییرات از قبل موجود `/Workspace`، layout و تست‌های
آن حفظ شده‌اند؛ registry، SSO، فرآیند پرداخت و فایل‌های چت‌های دیگر تغییر نکرده‌اند.
نیاز به API مرکزی و مسیر acquisition با اجازهٔ صریح کاربر برای چت
`Fanasa Platform Control Center` آماده شد. ارسال‌های اولیه بدون پاسخ ابزار متوقف
شدند؛ در پیگیری همین روز، ارسال پیام کوتاه با پاسخ موفق و شناسهٔ همان چت تأیید شد.
تحویل پیام با پیاده‌سازی API یکی نیست؛ قرارداد و endpoint هنوز اعلام نشده‌اند.
بدون دریافت پاسخ معتبر مرکزی، اتصال محیط واقعی کامل اعلام نمی‌شود.

کتاب برند رسمی در این نوبت با ابزار وب قابل خواندن نبود؛ همان نشان‌ها، فونت Vazir
و tokenهای موجود حفظ شده‌اند و تأیید تازهٔ برندبوک یا طرح نشان تازه ادعا نمی‌شود.
برد عملیاتی در ابزارهای این نشست موجود نیست؛ این سند شواهد محلی است، نه ثبت روی برد.

## آزمون‌ها

```powershell
dotnet run --project products/Fanasa.UnifiedPortal/tests/Discovery.Tests -c Release -- --http
node --test products/Fanasa.UnifiedPortal/tests/service-catalog.test.cjs products/Fanasa.UnifiedPortal/tests/portal-client.test.cjs
```

transport مرکزی و هویت‌ها در تست‌ها مصنوعی و فقط در اسمبلی آزمون‌اند. تست HTTP
میزبان موقت loopback را بعد از بررسی متوقف می‌کند؛ این شاهد API مستقر، خرید واقعی،
ورود SSO یا پذیرش دیداری نیست. اتصال واقعی نیازمند کاتالوگ منتشرشده و request URL
معتبر از مرکز راهبری، کاربر مجاز و بدون مجوز و محصول واقعی با consumer متفاوت است.

## شواهد اجرای این مرحله

- وب با صفر خطا و هشدار کامپایل شد. suite جدید در آخرین اجرا ۴۷ بررسی موفق داشت:
  ۴۰ بررسی قرارداد، adapter و PageModel و ۷ بررسی HTTP واقعی میزبان loopback.
- هر ۱۹ تست JavaScript موفق شد: ۱۲ regression قبلی و ۷ بررسی نمایش/درخواست/ورود.
  اجرای ترکیبی اولیه در sandbox به `spawn EPERM` برخورد کرد؛ اجرای مجاز بعدی موفق بود.
- suite موجود workspace در ورک‌اسپیس فعلی با ۷۰ بررسی موفق بود؛ بخشی از آن مربوط
  به تغییرات قبلی `/Workspace` است که در این کامیت وارد نمی‌شوند.
- در مرحلهٔ اولیه شناسایی مرورگر timeout داد؛ در پیگیری انتشار، مرورگر متصل شد و
  فیلتر مراکز، تازه‌سازی و نمایش موبایل نسخهٔ مستقر بررسی شدند.
- metadata واقعیِ همه سرویس‌ها و جریان واقعی acquisition هنوز دریافت/پذیرفته نشده‌اند.
  اتصال واقعی مرکزی هنوز پذیرفته نشده است. بخش Portal از کامیت `4f99dc8` روی
  VPS توسعه منتشر و صحت وضعیت `NotConfigured` آن بررسی شد؛ این نتیجه را موفقیت
  اتصال کاتالوگ واقعی نمی‌نامیم. شواهد در `SERVICE-DISCOVERY-DEPLOYMENT-2026-10-12.md` است.
- برای حفظ staged files سایر چت‌ها، کامیت فقط با index موقتِ این قابلیت و هانک‌های
  متعلق به آن آماده می‌شود؛ فایل‌ها و staging کارهای دیگر حفظ می‌شوند.

## پیگیری ۱۴ اکتبر ۲۰۲۶

بررسی تازهٔ VPS توسعه، سلامت release `4f99dc8` و no-store پاسخ ناشناس را تأیید
کرد؛ DiscoveryPath همچنان تعریف نشده بود. پیگیری قرارداد API به مالک مرکز
راهبری تحویل شد. نقص مستقل خواندن پاسخ رفع شد: IOException هنگام دریافت توکن
یا قطع بدنهٔ کاتالوگ، Unavailable می‌شود و هیچ metadata ناقصی برنمی‌گرداند؛
خرابی discovery نباید workspace مستقلاً تأییدشده را از بین ببرد.

۵۰ بررسی .NET و HTTP (سه بررسی جدید) و ۷ آزمون JS کاتالوگ موفق شدند. اجرای
اول .NET طولانی و بدون نتیجه لغو شد؛ اجرای بعدی با یک node و بدون queryهای
اختیاری SourceLink/SCM موفق شد. آزمون‌ها از ورک‌اسپیس فعلی‌اند؛ بستهٔ release
باید از سورس کامیت‌شدهٔ مستقل ساخته شود و شامل فایل‌های dirty Workspace نباشد.
۲۳ آزمون renderer مستقل مصرف نیز موفق شدند؛ wiring مالی هنوز انجام نشده است.
بازبینی و مرز مالکیت آن در `USAGE-ADAPTER-REVIEW-2026-10-14.md` ثبت شده است.

سپس همان سورس isolated با ۵۰ بررسی discovery و ۴۹ رگرسیون و ۱۹ آزمون Node
پذیرفته و کامیت `775605b` در development منتشر شد. health و پاسخ ناشناس
no-store روی VPS و HTTPS canonical از رایانه تأیید شدند. نسخه قبلی برای
rollback حفظ شد؛ metadata مرکزی و reader مالی هنوز متصل نیستند. شواهد در
`SERVICE-DISCOVERY-DEPLOYMENT-2026-10-14.md` ثبت شده‌اند.
