# اتصال فضای کار پنجره واحد

## قرارداد

- مرجع سازمان‌ها و محصولات فقط مرکز راهبری پلتفرم فن آسا است.
- پنجره واحد با کلاینت سرویس خودش، token با scope `platform.catalog` دریافت می‌کند.
- توکن باید audience مورد انتظار API مرکزی را داشته باشد.
- خواندن عضویت و محصول بر اساس subject استخراج‌شده از کوکی ورود انجام می‌شود.
- سازمان انتخابی مجدداً با فهرست مجاز تطبیق داده می‌شود؛ محصولات سازمان دیگر نمایش داده نمی‌شوند.
- برای یک سازمان انتخاب خودکار است؛ برای چند سازمان انتخاب صریح لازم است.
- پاسخ فضای کار `no-store` است و در مرورگر یا سرور بین کاربران cache نمی‌شود.
- خطای ارتباط یا مجوز با فهرست خالی موفق یکسان نیست.
- قرارداد خواندن: `GET /api/platform/application-tenants?subject=...` و
  `GET /api/platform/products?subject=...&tenant=...`؛ `tenant` مصرف‌کننده است.
- `TenantId` خود محصول، تننت تولیدکننده/مالک است. فیلتر کردن محصول با مقایسه آن
  با تننت مصرف‌کننده، محصول SaaS مجاز را اشتباه حذف می‌کند. مجوز عرضه/مصرف را API
  مرکزی اعمال می‌کند؛ پاسخ پنجره واحد به تننت درخواست‌شده وابسته می‌ماند.

## یافته استقرار توسعه — ۲۰۲۶-۱۰-۰۸

این بخش سابقه تشخیص با قرارداد قدیمی است؛ نتیجه استقرار و آزمون ۲۰۲۶-۱۰-۱۰
در انتهای سند، درخواست تغییر مجوز مبتنی بر این تشخیص را جایگزین می‌کند.

روی VPS، token endpoint برای کلاینت `fanasa-unified-portal-service` پاسخ موفق داد،
اما مخاطب توکن `account` بود و endpoint عضویت پاسخ HTTP 401 داد.
این مشاهده بدون تغییر عضویت، grant یا مجوز سامانه مرکزی انجام شد.
درخواست صریح scope `platform.registry` نیز از token endpoint پاسخ HTTP 400 گرفت؛
پیکربندی scope کلاینت فعلی باید در سامانه مرکزی تکمیل شود.

در کد فعلی مرکز راهبری، `PlatformService` فقط کلاینت
`fanasa-developer-service` با scope `platform.registry` را می‌پذیرد و
audience مورد انتظار `fanasa-access-management-web` است.

### درخواست هماهنگی قبلی — پیش از تطبیق دو نسخه

1. audience mapping کلاینت سرویس پنجره واحد برای API مرکزی تصحیح شود.
2. scope موردنیاز روی همان کلاینت مجاز باشد.
3. فقط GETهای `memberships` و `products`، سرویس پنجره واحد را در policy خواندن
   بپذیرند. policy نوشتن و ثبت محصول مختص سرویس توسعه‌دهنده باقی بماند.
4. با subject کاربر واقعی، عضویت فعال و دسترسی مصوب بررسی شود؛ برای پُر کردن
   کمبو سازمان یا مجوز ساختگی ایجاد نشود.
5. آزمون مجاز/غیرمجاز و چندتننت انجام شود و تغییرات در مخزن آن سامانه ثبت شوند.

تغییرات بالا در این چت اعمال نشده‌اند؛ دامنه این چت فقط پنجره واحد است.

## پیگیری — ۲۰۲۶-۱۰-۰۹

با تأیید صریح کاربر، درخواست اصلاح اتصال برای چت مالک با عنوان
`Fanasa Platform Control Center` ارسال شد. این ارسال به معنی تکمیل اصلاح مجوزها
یا تأیید اتصال واقعی نیست. پنجره واحد تا دریافت موفق پاسخ مرکزی، شمارنده و پیام
فهرست خالی موفق را نمایش نمی‌دهد؛ وضعیت خطای اتصال/مجوز مستقل نمایش داده می‌شود.

## اختلاف نسخه و اصلاح مصرف‌کننده — ۲۰۲۶-۱۰-۰۹

سند انتقال دانش مرکز راهبری و کد ورک‌تری منبع `8f13/Neo` قرارداد دیگری را نشان
دادند: policy اختصاصی `PlatformCatalog` با scope `platform.catalog`، endpoint
`application-tenants` و محصولات وابسته به پارامتر `tenant`. endpoint `memberships`
همچنان متعلق به `PlatformService` توسعه‌دهنده است. بنابراین تشخیص قبلی مبتنی بر
کد پوشه فعلی، برای الزام تغییر مجوز در نسخه مستقر کافی نیست.

کد پنجره واحد با قرارداد کاتالوگ فوق تطبیق داده شد؛ هیچ policy، کلاینت Keycloak،
grant یا عضویت در مرکز راهبری تغییر نکرد. پیش از درخواست تغییر امنیتی باید نسخه
مستقر با این قرارداد تطبیق داده شود. scope پیش‌فرض به `platform.catalog` تغییر کرد؛
override صریح محیط نیز باید همین قرارداد مصوب را داشته باشد، نه scope توسعه‌دهنده.

در این مرحله بررسی SSH زنده به مهلت بازبینی خودکار ابزار برخورد کرد. این مسئله
خطای API یا رد مجوز سرور نیست؛ اتصال واقعی و انتشار این اصلاحات هنوز از این شاهد
تأیید نمی‌شوند. پذیرش واقعی نیازمند کاربر مجاز، کاربر بدون grant و محصول SaaS با
مالک متفاوت از مصرف‌کننده است؛ فهرست خالی subject آزمایشی آن را اثبات نمی‌کند.

آزمون HTTP ناشناس روی میزبان رسمی `platform.fanasa.net.local` برای
`application-tenants` پاسخ 401 داد؛ مسیر در این میزبان قابل دسترس و محافظت‌شده است.
این بررسی بدون credential انجام شد و audience/scope کلاینت یا داده کاربر واقعی
را تأیید نمی‌کند. ۴۹ بررسی محلی، قرارداد scope، انتخاب صریح/خودکار تننت، رد تننت
دستکاری‌شده، محصول SaaS با مالک متفاوت و خطای عدم تطبیق پاسخ را پوشش دادند.

## استقرار و پذیرش توسعه — ۲۰۲۶-۱۰-۱۰

نسخه `499ac1cd9ae4f619fb9e61ba03b6f267b5867e78` با اسکریپت موجود انتشار، روی
VPS برای `fanasa-unified-portal@development` فعال شد. نسخه قبلی
`8c4c70c594ceb100cce5330e54f05e41a9276eea` برای بازگشت محفوظ است.
این انتشار شامل تغییر محیط production، سرویس مرکز راهبری، policyهای Keycloak،
عضویت یا grant نبود. پاسخ HTTPS مسیر `/health/live` برابر `Healthy` بود.

### قرارداد واقعی سرویس

- کلاینت اختصاصی: `fanasa-unified-portal-service`.
- scope: `platform.catalog`؛ audience: `fanasa-access-management-web`.
- دریافت توکن با scope فوق HTTP 200 داد؛ ادعاهای scope، audience و کلاینت
  اختصاصی تأیید شدند، بدون ثبت خود توکن یا credential.
- هر دو endpoint `application-tenants` و `products` با subject آزمایشی ناموجود
  HTTP 200 و پاسخ خالی دادند؛ درخواست ناشناس API مرکزی HTTP 401 داد.
- درخواست ناشناس `/?handler=Workspace` در پنجره واحد HTTP 200 با وضعیت
  `SignInRequired` و `Cache-Control: no-store` داد؛ این پاسخ داده سازمان نیست.

بنابراین برای اتصال به قرارداد کاتالوگ موجود، تغییر مجوزهای مرکزی لازم نبود.
درخواست هماهنگی قبلی، پیش از تطبیق نسخه و قرارداد ایجاد شده بود و الزام فعلی
برای گسترش دسترسی محسوب نمی‌شود. پاسخ خالی subject آزمایشی فقط دسترس‌پذیری و
احراز هویت سرویس را اثبات می‌کند، نه مجوز کاربر واقعی.

### مرورگر و حساب واقعی

- ورود مستقیم از پنجره واحد با نشست موجود SSO مرکزی و بازگشت به میزبان رسمی
  `https://hub.fanasa.net.local/` موفق بود؛ رمز جدیدی وارد یا ذخیره نشد.
- فهرست «سازمان فعال» با سازمان مجاز پر شد و انتخاب خودکار تک‌سازمانی کار کرد.
- «تازه‌سازی فهرست» از وضعیت دریافت به پاسخ نهایی بازگشت. مسیر JavaScript
  از `fetch` و `history.replaceState` استفاده می‌کند و submit عادی را لغو می‌کند.
- انتخاب سازمان نامجاز با شناسه صفر، پیام عدم دسترسی و حالت انتخاب سازمان
  نشان داد؛ هیچ لینک سامانه‌ای نمایش داده نشد. انتخاب سازمان مجاز از کمبو،
  فضای کار مجاز را دوباره دریافت کرد.
- برای حساب واقعی آزمایش‌شده، کاتالوگ مرکزی در سازمان مجاز صفر سامانه برگرداند
  و پیام «هنوز سامانه‌ای ... فعال نشده است» نمایش داده شد، نه خطای ارتباط.

هیچ ایمیل، subject واقعی، token، credential یا پاسخ خام در این سند ذخیره نشده است.
خالی بودن کاتالوگ به‌تنهایی علت را مشخص نمی‌کند؛ ثبت محصول، عرضه، grant مصرف و
اعتبار زمانی باید در چت مالک مرکز راهبری بررسی شوند. برای پُر کردن صفحه، محصول
یا دسترسی ساختگی ایجاد نشده است. نمایش و باز کردن سامانه مجاز، رد کاربر بدون
grant و سناریوی واقعی SaaS با تولیدکننده متفاوت هنوز پذیرش کامل نشده‌اند؛
پوشش محلی این سناریوها جای آزمون واقعی آن‌ها را نمی‌گیرد.
