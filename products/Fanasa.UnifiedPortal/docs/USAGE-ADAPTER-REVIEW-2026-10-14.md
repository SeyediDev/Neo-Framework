# بازبینی قرارداد نمایش مصرف Workspace — ۱۴ اکتبر ۲۰۲۶

## محدوده و نتیجه

سه فایل بستهٔ مستقل مصرف (`WorkspaceUsageReportAdapter.cs`،
`usage-report-view.js` و README آن) کامل خوانده و با مدل فعلی `WorkspaceJourney.cs`،
`WorkspaceModel` و `renderUsage` / `renderMetrics` تطبیق داده شدند.
فایل‌های متعلق به مالک Workspace، اتصال مالی، scope، grant و انتشار او تغییر نکردند.

قرارداد بسته برای **نمایش محدودِ هزینهٔ مصرف ثبت‌شده** قابل پذیرش است، اما
با DTO فعلی Portal سازگار نیست و پذیرش آن به معنای اتصال عملیاتی نیست.
mapper، subject/consumer/دو مرز دقیق UTC را با envelope معتبر تطبیق می‌دهد؛
در ناسازگاری، اطلاعات مالی حذف می‌شوند. مبلغ‌ها رشتهٔ اعشاری دقیق‌اند؛
جمع ردیف‌ها و دقت ارز کنترل می‌شود. renderer دادهٔ سازمان قبلی را پاک می‌کند،
نام‌ها را با textContent نشان می‌دهد و صفر واقعی را از گزارش ثبت‌نشده جدا می‌کند.

۲۳ آزمون مستقل Node همین renderer در این نوبت موفق شدند. این اجرای تازه بدون
fixtures صادرشده و بدون شبکه بود؛ ۲۴ گروه/۱۱۶ assertion/۱۹ گروه مرورگر در
شاهد قبلی بسته، نتایج مالک آن بسته‌اند و در این نوبت دوباره اجرا نشده‌اند.

## موارد قابل اقدام نزد مالک Workspace

1. **مدل:** `WorkspaceUsageItem` فاقد ProductKey، MeterId، MeterVersion و ChargeCount
   است و Quantity/Unit را غیرnullable و Quota را الزامی می‌گیرد. خروجی تازه به آن
   cast نشود. nullهای legacy باید «نامعلوم» بمانند، نه صفر یا سهمیهٔ ساختگی.
2. **آمار:** `renderUsage` تعداد ردیف‌ها را تعداد خدمات می‌نامد. تعداد خدمات باید
   از ProductKeyهای متمایز به دست آید؛ ردیف‌های متر/نسخه/واحد جدا حفظ شوند.
3. **مفهوم مالی:** ستون «سقف طرح» از renderer قدیمی حذف شود، مگر منبع مستقل و
   تأییدشدهٔ entitlement/quota موجود باشد. basis گزارش `posted-ledger` است؛
   گزارش مصرف، موجودی کیف پول، سهمیه، صورتحساب یا پرداخت نیست.
4. **وضعیت‌ها:** ready / notRecorded / incomplete / unavailable باید در tab و
   متریک با معنای خود نمایش داده شوند. اعلان ثابت `usage-connection-notice` در
   cshtml حتی پس از موفقیت واقعی باقی نماند. حالت notConnected فعلی، حالت اتصال
   Portal است و بدون خواندن معتبر نباید به ready یا صفر تبدیل شود.
5. **دوره:** `IWorkspaceJourneySource.GetAsync` فعلی پارامتر from/to ندارد.
   انتخاب «این ماه»/«ماه قبل» با مرز واقعی UTC و بازهٔ نیمه‌باز `[from,to)` هماهنگ
   شود. پاسخ دیررس فقط برای subject، consumer، دوره و نسل درخواست همچنان فعال
   اعمال شود؛ کنترل organization در renderer به‌تنهایی کنترل دوره نیست.
6. **نمایش مشترک:** `renderMetrics` نیز مقدار را از همان گزارش معتبر و دقیق بخواند،
   نه صرفاً از status قدیمی یا دادهٔ preview. جدول/متریک/پیام اتصال یک وضعیت داشته باشند.
7. **مرز اسمبلی:** mapper نمونه به نوع ConsumerUsageReport در namespace مرکزی
   وابسته است و project reference به Web مرکزی فقط در harness آزمون آن آمده است.
   Portal نباید برای استفاده از این نمونه به اسمبلی Web مرکز راهبری وابسته شود؛
   قرارداد انتقال نسخه‌دارِ مستقل یا DTO محلیِ مطابق API مصوب لازم است.

## محل پیشنهادی اتصال — هنوز پیاده‌سازی نیست

پس از تحویل API مصوب، reader مالی مستقل در سمت سرور Portal و در کنار خواندن
workspace قرار گیرد؛ ورودی‌اش subject نشست، سازمان مصرف‌کنندهٔ تأییدشده و دو
مرز دوره باشد. شکست مصرف نباید فهرست سرویس‌های مجاز را از بین ببرد.
خروجی محدود با camelCase به Bootstrap مصرف اضافه/مدل فعلی با هماهنگی مالک
تکامل داده شود؛ serializer پیش‌فرضِ ایمن برای HTML حفظ شود و subject/delegation
token به مرورگر نرود. renderer مستقل در container تب مصرف جایگزین نمایش قدیمی
شود و منطق metریک‌ها به همان DTO معتبر متصل گردد.

این پیشنهاد مجوز تغییر فایل‌های چت مالک Workspace یا انتخاب API/روش delegation
به جای مالک مرکزی نیست؛ گزارش نهایی همین بازبینی در این چت نیز قابل خواندن است.

## وابستگی مالی واقعی

مالک مرکز راهبری باید route/DTO نسخه‌دار و روش delegation محدود را اعلام کند،
reader را به Fabric عملیاتی موجود وصل کند و عضویت و مجوز زندهٔ `billing.read`
را برای consumer/subject واقعی بررسی کند. service token یا subject دلخواهِ فرم
اثبات نمایندگی کاربر نیست. `platform.catalog` مجوز خواندن مالی نیست.
API حسابداری فعلی نیازمند نشست انسانی و مجوز مالی است؛ صفحهٔ Accounting یا
reconciliation ادمین، جای قرارداد گزارش مصرف‌کنندهٔ Portal نیست.

پس از آن، تغییر سازمان/دوره، لغو مجوز، logout، outage و پاسخ دیررس باید بدون
حفظ مبلغ سازمان قبلی پذیرفته شوند. ورود به سازمان برای catalog به‌تنهایی اثبات
مجوز گزارش مالی نیست. هیچ مسیر HTTP، scope مالی، grant یا مبلغ عملیاتی حدس زده نشد.

## وضعیت مستقل کاتالوگ معرفی

بررسی read-only VPS در همین نوبت نشان داد Portal development فعال است و
`/health/live` با HTTP 200 / Healthy پاسخ می‌دهد. release آن همچنان `4f99dc8` است.
DiscoveryPath در محیط موجود نیست؛ پاسخ ناشناس `SignInRequired`، no-store و
کاتالوگ `NotConfigured` است و هیچ organization/product خصوصی ندارد.
پیگیری نیاز API معرفی با نتیجهٔ موفق ابزار به چت `Fanasa Platform Control Center`
تحویل شد. این وابستگی از اتصال مالی بالا مستقل است.

در ادامهٔ همین نوبت، مقاوم‌سازی مستقل discovery از کامیت `775605b` منتشر شد؛
شواهد در `SERVICE-DISCOVERY-DEPLOYMENT-2026-10-14.md` است. اتصال مالی یا فایل‌های
Workspace همراه آن منتشر/تغییر نکردند و discovery همچنان NotConfigured ماند.
