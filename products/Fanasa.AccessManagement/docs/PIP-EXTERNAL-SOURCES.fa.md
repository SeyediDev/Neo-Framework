# اتصال اطلاعات مرجع به سیاست دسترسی

PIP اطلاعات لازم برای تصمیم را از مرجع مشخص دریافت می‌کند. مثلاً «همکاری این فرد هنوز فعال است» باید از سامانهٔ منابع انسانی بیاید. هویت، منبع و زمان مشاهده همراه داده ثبت می‌شوند؛ کاربر درخواست دسترسی نمی‌تواند ویژگی دلخواه خود را به موتور تحمیل کند. ثبت منبع یا دریافت موفق داده به‌تنهایی مجوز ایجاد نمی‌کند.

تعریف منبع و نگاشت داده در **سازمان ← اطلاعات معتبر PIP** است (`/Organization?tenant=<tenant-id>#organization-pip`). تعریف قاعده و آزمایش آن در **سیاست و تصمیم دسترسی** است (`/Governance?tenant=<tenant-id>#policy-authoring`). تقویم، ساختار، عضویت و انتصاب موجود همچنان مراجع محلی‌اند؛ این قابلیت ورودی خارجی ویژگی‌های هویت را به آن‌ها اضافه می‌کند.

## نمونهٔ قابل اجرا در سازمان الگو

مدیر پلتفرم در سازمان دارای نشان «سازمان الگو»، دکمهٔ «آماده‌سازی نمونهٔ آموزشی و دادهٔ تازه» را اجرا می‌کند. این عملیات:

1. یک منبع نشان‌دار و مصنوعی ایجاد می‌کند؛ `example.invalid` نشانی توضیحی است و هیچ درخواست شبکه‌ای به آن انجام نمی‌شود.
2. دو عضویت مصنوعی محلی، یکی با داده و یکی بدون داده، ایجاد می‌کند. برای آن‌ها حساب Keycloak یا مجوز مستقیم ساخته نمی‌شود.
3. دادهٔ `employment.active = true` و `organization.unit = engineering` را برای هویت نمونه با عمر ۳۰۰ ثانیه ثبت می‌کند.
4. یک سیاست **پیش‌نویس** برای عملیات `tenancy.read` می‌سازد. سیاست منتشر نمی‌شود و گزینهٔ اجرای زنده خاموش است.
5. سه سناریو را با موتور واقعی سرور اجرا می‌کند: دادهٔ تازه → `Permit`؛ رسیدن به پایان اعتبار → `Indeterminate`؛ عضو فعال بدون داده → `Indeterminate`.

هویت دارای داده `urn:fanasa:example:pip:reader` است. در فرم آزمایش، همین هویت، عملیات `tenancy.read` و گزینهٔ «پیش‌نویس‌ها هم فقط در این آزمایش بررسی شوند» را انتخاب کنید. زمان خالی یعنی ساعت فعلی سرور؛ پس از پنج دقیقه، ابتدا دادهٔ نمونه را تازه کنید. نتیجهٔ سناریو و آزمایش همواره شبیه‌سازی است (`enforced: false`). تازه‌سازی نمونه، منبع، عضویت و سیاست تکراری نمی‌سازد؛ نمونهٔ ناسازگار را نیز خودکار بازنویسی نمی‌کند. سیاست‌ها و سناریوهای قبلی سازمان الگو تغییر نمی‌کنند.

## اتصال واقعی، از مسئول داده تا اولین دریافت

ابتدا مسئول داده باید نشانی HTTPS، شناسهٔ پایدار افراد، نام فیلدها، انواع، نسخه و زمان معتبر مشاهده را مشخص کند. سرویس مرجع باید بتواند درخواست یک هویت در یک سازمان را پاسخ دهد. شناسهٔ هویت باید با subject عضویت همان سازمان برابر باشد؛ نام نمایشی جای آن را نمی‌گیرد.

مدیر استقرار یک اتصال دقیق برای **شناسهٔ سازمان + نشانی کامل endpoint + نام مرجع رمز** در تنظیمات سرور ثبت می‌کند. مدیر سازمان با نوشتن دامنه در فرم نمی‌تواند این اعتماد شبکه را ایجاد کند. نمونهٔ تنظیمات زیر را با شناسه و نشانی مصوب واقعی جایگزین کنید؛ مقدار رمز در این فایل نیست:

```json
{
  "Pip": {
    "Transport": {
      "Bindings": [
        {
          "TenantId": "11111111-1111-1111-1111-111111111111",
          "Endpoint": "https://hr.example.test/attributes",
          "SecretReference": "hr-reader",
          "AllowedPrivateAddresses": []
        }
      ]
    }
  }
}
```

راز متناظر با `hr-reader` از کلید پیکربندی `Pip:Secrets:hr-reader`، مثلاً متغیر محیطی `Pip__Secrets__hr-reader` در محیط استقرار، خوانده می‌شود. مقدار آن یک bearer token است؛ آن را در Git، نشانی سرویس یا فرم منبع نگذارید. منبع بدون احراز هویت باید هم در اتصال مصوب و هم در تعریف منبع، `SecretReference` خالی داشته باشد. نام مرجع و endpoint باید دقیقاً با اتصال مصوب همان سازمان تطبیق داشته باشند. نبود اتصال مصوب یا راز حل‌شده، دریافت را متوقف می‌کند.

اتصال به نشانی‌های عمومی واجد شرایط به‌صورت پیش‌فرض ممکن است. برای یک سرویس داخلی، فقط IP خصوصی مشخص RFC1918 یا IPv6 ULA را در `AllowedPrivateAddresses` همان اتصال ثبت کنید. نام میزبان همچنان باید با گواهی TLS معتبر سرویس سازگار باشد. loopback، link-local و نشانی‌های metadata با این استثنا باز نمی‌شوند. تمام پاسخ‌های DNS پیش از اتصال بررسی می‌شوند و اتصال به همان IP بررسی‌شده برقرار می‌شود؛ redirect و proxy خودکار غیرفعال‌اند.

سپس در پنل سازمان منبع را تعریف کنید:

| فیلد | مثال | دلیل انتخاب |
| --- | --- | --- |
| نام و مسئول | وضعیت همکاری · منابع انسانی | مشخص‌بودن مسئول اعتبار داده |
| endpoint / میزبان | `https://hr.example.test/attributes` / `hr.example.test` | بدون query، رمز یا fragment |
| نسخهٔ قرارداد | `1` | نسخهٔ پشتیبانی‌شدهٔ فعلی |
| حداکثر عمر | `300` ثانیه | از observedAt مرجع محاسبه می‌شود |
| مهلت پاسخ | `10` ثانیه | جلوگیری از انتظار نامحدود |
| سقف پاسخ | `262144` بایت | پاسخ محدود، بدون فشرده‌سازی |
| فاصلهٔ دریافت | `60` ثانیه | صفر برای دریافت دستی؛ زمان‌بندی از ۳۰ ثانیه |
| هویت‌های زمان‌بندی | هر خط یک subject | دریافت برای هر هویت مستقل است |

منبع از فرم با وضعیت غیرفعال ثبت می‌شود. پس از بررسی اتصال و قرارداد آن را همراه دلیل فعال کنید، اولین هویت را دریافت کنید، و «بررسی تازگی دادهٔ این هویت» را اجرا کنید. آخرین دریافت موفق یک منبع به معنی تازه‌بودن دادهٔ همهٔ هویت‌ها نیست. سوابق اجرا، هویت، زمان، نتیجه، علت کنترل‌شده و اثر انگشت snapshot را نشان می‌دهند.

## قرارداد پاسخ و نگاشت ویژگی

آداپتور درخواست `GET` را با پارامترهای `tenantId` و `subject` که خود سرور می‌سازد ارسال می‌کند. پاسخ باید HTTP 200 با `Content-Type: application/json` و بدون فشرده‌سازی باشد. نمونه:

```json
{
  "schemaVersion": 1,
  "tenantId": "11111111-1111-1111-1111-111111111111",
  "subject": "employee-001",
  "sourceVersion": "hr-event-42",
  "observedAt": "2026-10-23T08:00:00Z",
  "attributes": {
    "activeEmployee": "true",
    "departmentCode": "engineering"
  }
}
```

این زمان ثابت فقط مثال است. سرویس واقعی باید زمان مشاهدهٔ معتبر خودش را با UTC صریح (`Z` یا `+00:00`) بفرستد. زمان دریافت شبکه جای زمان مشاهدهٔ داده را نمی‌گیرد. دادهٔ ازقبل‌منقضی یا زمان آیندهٔ نامعتبر پذیرفته نمی‌شود.

در فرم نگاشت، `activeEmployee` را به نام ثابت `employment.active` با نوع `boolean` و گزینهٔ لازم، و `departmentCode` را به `organization.unit` با نوع `string` متصل کنید. نوع‌های پشتیبانی‌شده `string`، `boolean`، `integer`، `decimal` و `datetime` هستند. **مقدار همهٔ ویژگی‌ها در JSON رشته است**؛ نوع اعلام‌شده روی همان رشته اعتبارسنجی می‌شود. boolean فقط `true` یا `false` است؛ عدد با قالب invariant و بدون جداکنندهٔ هزارگان، و datetime با UTC صریح ارسال می‌شود.

نام ویژگی و فیلد خارجی حداکثر ۱۰۰ نویسه دارد، با حرف لاتین شروع می‌شود و فقط حرف، عدد، نقطه، خط تیره و زیرخط می‌پذیرد. نام‌های حاوی password، secret یا token مجاز نیستند. فیلد ناشناخته یا تکراری، ویژگی اعلام‌نشده، نوع نامعتبر، ویژگی لازمِ مفقود، سازمان یا هویت ناهماهنگ، و نسخهٔ تکراری با محتوای متفاوت رد می‌شود. hash و provenance از محتوای نرمال‌شده در سرور ساخته می‌شوند؛ سامانهٔ خارجی نباید آن‌ها را به envelope اضافه کند.

هر snapshot به سازمان، منبع و هویت مشخص متصل است. تغییر معتبر داده باید نسخهٔ تازه و observedAt جلوتر داشته باشد. بازپخش نسخهٔ قبلی، نسخهٔ یکسان با محتوای متفاوت یا دادهٔ قدیمی، جای دادهٔ جدید را نمی‌گیرد. ETag برای همان snapshot هویت استفاده می‌شود؛ پاسخ 304 عمر داده را تمدید نمی‌کند.

## اتصال ویژگی به سیاست

در بخش سیاست، قالب «ویژگی معتبر از منبع اطلاعات PIP»، منبع همین سازمان، ویژگی `employment.active` و مقدار `true` را انتخاب کنید. شرط برابری نوع‌دار است و فقط snapshot معتبر و تازهٔ همان هویت را مصرف می‌کند. فرم درخواست، نقش یا ویژگی ادعاشده از سمت کاربر دریافت نمی‌کند.

در این پروفایل، نبود منبع معتبر، نبود snapshot، انقضا، ناسازگاری قرارداد یا نبود ویژگی موردنیاز قاعده، `Indeterminate` می‌دهد؛ مجوز مستقیم آن نقص را دور نمی‌زند. دریافت ناموفق، snapshot معتبر قبلی را پاک نمی‌کند؛ آن داده فقط تا پایان اعتبار اصلی و با کنترل‌های فعلی قابل مصرف است. مقدار معتبر نابرابر، یعنی قاعده تطبیق ندارد. بنابراین قاعدهٔ Permit برای active=true به‌تنهایی مفهوم «فقط کارکنان فعال، حتی دارندگان مجوز مستقیم» را تضمین نمی‌کند؛ سیاست منع مناسب برای active=false و ترکیب قواعد را نیز آزمایش کنید.

پیش‌نویس فقط در آزمایش صریح مدیر بررسی می‌شود. انتشار مستقل، فعال‌بودن قابلیت اجرای سازمان و پشتیبانی مسیر API همچنان شرایط جداگانهٔ اجرای زنده‌اند. PIP راهی برای ساخت claim، دورزدن API Gateway یا فعال‌کردن خودکار سیاست نیست.

اتصال اجرای زنده از فهرست مجاز سازمان‌ها در تنظیمات موجود `Organization:TemporalAccess` استفاده می‌کند و محدودهٔ فعلی آن `organization.read` و `organization.write` در مسیرهای پشتیبانی‌شدهٔ سازمان/HR است. عملیات دیگر، از جمله `tenancy.read` نمونهٔ آموزشی، در این بخش فقط تعریف و شبیه‌سازی می‌شوند مگر آنکه میزبان صریحاً نقطهٔ اعمال تصمیم آن عملیات را متصل کند. این قابلیت به معنی اعمال خودکار سیاست روی همهٔ مسیرهای API Gateway نیست. برای محدودکردن مجوز مستقیم به همکاری فعال، قاعدهٔ Deny روی `employment.active = false` باید گزینهٔ اجرای زنده داشته باشد و تمام شرایط انتشار و فعال‌سازی همین مسیر را طی کند.

## محدودهٔ فعلی

- ورودی خارجی این نسخه، HTTPS JSON برای ویژگی‌های subject با دریافت دستی یا زمان‌بندی هویت‌های مشخص است. LDAP، SCIM، پیام‌صف، CDC، CSV و تبدیل عمومی JSONPath آداپتور آماده ندارند.
- این ورودی خارجی جایگزین هویت مرکزی، منبع ساختار سازمان یا تقویم تعطیلات نیست. ویژگی عمومی resource/environment از این فرم وارد نمی‌شود.
- اسرار، اتصال شبکه و گواهی TLS از تنظیمات استقرار می‌آیند. ساخت فرم یا اجرای نمونهٔ مصنوعی اثبات اتصال به سامانهٔ واقعی نیست.
- تعریف منبع و قرارداد برای تغییرات اساسی با منبع جدید انجام می‌شود؛ سیاست باید به منبع تازه ارجاع دهد و مستقل بررسی شود. غیرفعال‌سازی منبع موجود در پنل در دسترس است.
- این موتور یک پروفایل محدود از مفاهیم XACML است، نه مفسر عمومی XML یا ادعای انطباق کامل استاندارد.

کنترل‌های JS در `tests/pip-ui.test.cjs` و `tests/pip-governance-ui.test.cjs`، و سناریوهای پایگاه داده در `Organization.Tests/PipEducationalTests.cs` نگهداری می‌شوند. صحت اتصال واقعی را با منبع مصوب، دریافت یک هویت آزمایشی، بررسی نسخه/تازگی و سپس ارزیابی سیاست اثبات کنید؛ نتیجهٔ تست محلی را به‌جای این شاهد عملیاتی گزارش نکنید.
