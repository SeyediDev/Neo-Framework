# پیش‌بررسی پیکربندی اتصال HR به PIP

این ابزار مستقل، سازگاری **طرح تنظیمات** را پیش از نصب بررسی می‌کند. فقط یک فایل JSON محلی بدون راز می‌خواند؛ درخواست شبکه، خواندن اعتبارنامه، تغییر پایگاه، grant، منبع، Gateway یا Git ندارد. در pipeline و runtime ادغام نشده است و بستهٔ پذیرفته‌شدهٔ r6 را تغییر نمی‌دهد.

## علت ساخت

بررسی موجود `deploy/fanasa-organization-hr/runtime_config.py` سلامت پیکربندی، پایگاه و TLS میزبان را بررسی می‌کند. این نتیجه، وجود reader مناسب یا اتصال HR→PIP→PDP را اثبات نمی‌کند. در چارت Kubernetes فعلی نیز خروجی شبکه فقط DNS و مقصد هویت است؛ دسترسی به Gateway و تزریق secret مصرف‌کننده را نباید از سلامت Pod نتیجه گرفت.

فایل `plan.example.json` کاملاً مصنوعی است: شناسه‌ها، دامنه‌های `.example.test` و IPها باید با طرح استقرار مصوب جایگزین شوند. هیچ رمز، توکن، کلید خصوصی یا محتوای گواهی را وارد آن نکنید. ابزار فیلد ناشناخته، کلید تکراری و بدنهٔ بزرگ‌تر از ۱MiB را رد می‌کند و خطاها را بدون نمایش ورودی برمی‌گرداند.

## اجرای محلی

```powershell
python -B deploy/fanasa-organization-hr/pip-preflight/pip_preflight.py --plan deploy/fanasa-organization-hr/pip-preflight/plan.example.json
python -B -m unittest discover -s deploy/fanasa-organization-hr/pip-preflight -p test_pip_preflight.py -v
```

کد خروج صفر یعنی طرح سازگار است؛ کد ۲ یعنی خطای ورودی یا ناسازگاری. `configurationValidated:true` فقط نتیجهٔ بررسی طرح است. `liveAccepted:false` و `networkPerformed:false` همیشه حفظ می‌شوند. مسیر secret و CA صرفاً مرجع‌اند؛ وجود فایل، صحت گواهی و دسترسی پردازه به راز بررسی نشده‌اند. DNS نیز resolve نمی‌شود؛ کنترل IP در زمان اتصال همچنان بر عهدهٔ transport واقعی است.

## قرارداد طرح

سه بخش اجباری وجود دارد: `provider`، `consumer` و `source`. ارائه‌دهندهٔ HR و مصرف‌کنندهٔ PIP ممکن است در دو پردازهٔ جدا باشند؛ برای هرکدام `runtime` را صریحاً `kubernetes` یا `systemd` تعیین کنید. این فیلد تصمیم نصب یا تغییر NetworkPolicy ایجاد نمی‌کند.

- reader فقط یک تننت، client و subject سرویس مشخص، audience محصول HR و scope `organization.hr.attributes.read` دارد. این طرحِ محدود، جایگزین قابلیت چندتننتی عمومی API نیست.
- tenant، client، scope، OAuth reference، مرجع secret، کلید تزریق محیطی، issuer و endpointهای منبع/توکن باید بین بخش‌ها منطبق باشند.
- مسیر منبع دقیقاً مسیر توسعهٔ `.../tenants/{tenantId}/attributes` است؛ نشانی HTTPS دارای query، fragment یا اعتبارنامه پذیرفته نیست.
- هر دو مقصد هویت و Gateway باید در فهرست خروجی مصرف‌کننده ذکر شوند. این فهرست، **اثبات نصب یا تأیید قانون شبکه نیست**. نصب قانون به محل اجرای مصرف‌کننده وابسته است؛ اگر مصرف‌کننده Web مبتنی بر systemd باشد، بازکردن egress در Pod ارائه‌دهنده لازم نیست.
- منبع قرارداد نسخهٔ ۲ و شش تعریف HR دارد: سه صفت اجباری عضویت/انتصاب و سه صفت اختیاری واحد/سمت/نقش. نوع، required و externalName دقیق بررسی می‌شوند. membership با employment یکی نیست.
- شناسه‌های شخص، تنظیم زمان‌بندی، مرجع CA مطلق POSIX و استثناهای دقیق RFC1918/ULA بررسی می‌شوند. literalهای loopback/link-local و مقصد خصوصی خارج از استثنا رد می‌شوند. مسیر CA برای استقرار Linux است؛ فایل روی Windows باز نمی‌شود.

فیلدهای واقعی ASP.NET را مطابق [قرارداد PIP](../PIP-ATTRIBUTES.md) تنظیم کنید. این فایل طرح، appsettings نیست و نباید مستقیماً به‌عنوان appsettings نصب شود.

## پذیرش زندهٔ باقی‌مانده

قالب `live-acceptance.template.json` یک فهرست کار با همهٔ بررسی‌ها در حالت `pending` است. ابزار آفلاین آن را به رسید موفق تبدیل نمی‌کند. مالک انتشار پس از نصب باید شاهد واقعی هر بررسی را با زمان، commit و شناسهٔ استقرار ثبت کند؛ راز یا بدنهٔ HR را در رسید نگذارد.

| بررسی | شاهد مورد نیاز |
|---|---|
| نسخه و تنظیم پردازه | commit/artifact دقیق و تنظیمات مؤثر همان provider و consumer |
| ثبت هویت | client/scopes/subject فعال و اختصاصی، عضویت همان تننت، grant خواندن و اشتراک معتبر |
| TLS و شبکه | CA و secret mount قابل دسترسی، خروجی محدود به دو مقصد، route دقیق و mTLS واقعی |
| قرارداد پاسخ | پاسخ نسخهٔ ۲ متعلق به شخص و تننت درخواست، شش تعریف سازگار، زمان و `validUntil` معتبر |
| رد درخواست | token نامعتبر/منقضی، تننت دیگر، subject نامعتبر، scope نامناسب و نبود mTLS رد شوند |
| مسیر کامل | آزمون اتصال snapshot نسازد؛ فعال‌سازی فقط با رسید معتبر؛ sync شاهد درست در DB بسازد و PDP آن را مصرف کند |
| پایان اعتبار | در پایان appointment یا `FreshUntil` تصمیم fail-closed شود؛ قطعی مرجع اعتبار cache را تمدید نکند |
| نسل و بازیابی | غیرفعال‌سازی شاهد را باطل کند؛ فعال‌سازی دوباره دریافت فوری بخواهد؛ restart داده و تنظیم را حفظ کند |

آزمون‌های دارای تغییر وضعیت فقط در تننت آزمایشی مصوب و از مسیر مالک انتشار انجام شوند. مجوز قدیمی منقضی به‌صورت خودکار تمدید نمی‌شود. عدم پاسخ یا نتیجهٔ سلامت سرویس، قبول هیچ‌یک از این بررسی‌ها محسوب نمی‌شود.
